# 工作流

方寸怎么一轮一轮往前走：谁在哪做什么、怎么交接、靠什么把关。这份文档自己也在迭代，见末尾「复盘」。

2026-11-14 建立。目标是交接不靠人传话、能自动查的不靠人眼。

## 角色与地点

| 谁 | 在哪 | 做什么 |
| --- | --- | --- |
| 人 | 任何地方 | 提需求、拍板、验收 |
| 本地 Agent | 本机 Claude Code | 改设计文档、实现、合并 PR、截图自查 |
| 云端 Agent | claude.ai 云端会话 | 改画布、同步原型。要用 Artifact 工具，本地没有 |
| Codex | 本机 | 操控桌面，规则见 `AGENTS.md`「Computer use」。能用脚本截图的，不用它 |

画布是 claude.ai 上的原型画布，地址在 `prototype/README.md`。

## 一轮迭代

```
 ① 设计 ───→ ② 原型 ───→ ③ 同步 ───→ ④ 实现 ───→ ⑤ 验收
 本地         云端画布      云端 → PR    本地 → PR    本机
   ↑                                                  │
   └──────── 设计问题回 ①，实现问题回 ④ ←─────────────┘
```

| 步 | 人说 | Agent 做 | 交给下一步的东西 | 把关 |
| --- | --- | --- | --- | --- |
| ① 设计 | 「改设计：…」 | 改 `product-design.md`。文档没写到的一件件问，每件至少三个选项、标推荐项。人确认后，原话记进 DECISIONS，要改原型的地方逐条写进 BACKLOG「原型待改」 | 合并后的 PR，带「原型待改」清单 | 人确认 |
| ② 原型 | 云端：「按原型待改改原型并同步」；或人自己在画布里改完，说「同步原型」 | 按清单改画布 | 画布的新版本 | — |
| ③ 同步 | （接着 ②） | 按下面「同步原型」做，最后开 PR | PR「原型同步 <版本>」 | `check.js`、CI |
| ④ 实现 | 「合并 #N」「实现 M0-22」 | 先 `pnpm workflow --fetch`。实现，`pnpm check`，`pnpm screens --compare` 对比，跟上的画板 `pnpm workflow accept` | PR，CI 过后合并 | 见「质量关」 |
| ⑤ 验收 | 「看一眼」 | 先自查：`pnpm screens --snapshot`、`pnpm window-shot`。再请人 `pnpm dev` 看 | 人的反馈，进 BACKLOG | 人 |

谁说了算的顺序（设计 → 原型 → 实现）见 `AGENTS.md`「谁说了算」。

## 口令

人说这些话时，Agent 不用再问要做什么。

| 口令 | 在哪说 | Agent 做 |
| --- | --- | --- |
| 看状态 | 本地 | `pnpm workflow --fetch`，按它的输出汇报，给出建议的下一步 |
| 改设计：… | 本地 | 第 ① 步 |
| 按原型待改改原型并同步 | 云端 | 第 ②、③ 步，做完开 PR |
| 同步原型 | 云端 | 第 ③ 步，做完开 PR |
| 合并 #N | 本地 | 看 PR 的改动和 CI，都过了就合并，再拉 main |
| 实现 <编号> | 本地 | 第 ④ 步 |
| 收工 | 两边 | `AGENTS.md`「收工前必须做的事」 |
| 复盘工作流 | 本地 | 本文「复盘」 |

## 交接规则

1. **交接物只有两种：PR 和 BACKLOG 条目。** 只写在对话里的东西，下一位看不到，等于没交接。
2. **云端会话收尾必须开 PR。** 开不了时，把 PR 标题和描述写在最后一条消息里，由人点「Create PR」，STATUS 里写明分支名。
3. **要人定、要人看的事一律进 BACKLOG「待人处理」。** 每条一句话；要选的给选项和推荐项。人可以一次批完。
4. **开工先看状态。** `pnpm workflow --fetch` 列出待人处理、没合并的云端分支、原型待改、落后的示例数据、没复盘的摩擦。

同步原型的 PR 描述照这个写：

```
画布版本：<旧> → <新>
改了哪些画板：…
对照第 6 节：没有不一致 / 不一致 N 处（列出，已进 BACKLOG）
文档没写到的：N 件（已进「待人处理」）
原型待改：完成 D-xx、D-yy
示例数据会落后的画板：Main、Global（CI 会提醒）
```

## 同步原型

在云端会话里做，要用 Artifact 工具。

1. 用 Artifact 工具 `list`（`scope: "files"`）列出画布文件。只要 `project/` 下的文件；`index.html`、`SKILL.md`、`artifact-type/` 是编辑器本身，不要。
2. 用 `read`，`paths` 填全部 `project/…` 路径，`out_dir` 填仓库的 `prototype`，一次读完。画布上已删除的画板，把本地对应文件也删掉。不要用网页抓取去读。
3. 改写 `prototype/README.md` 的同步记录，版本号取 `read` 结果里的 version。新增或删掉画板时，改它的画板表。
4. 在仓库根目录运行 `node tools/prototype-preview/check.js`。它用预览器渲染每张画板，重新生成 `prototype/screens/`。没有全部通过（有报错、残留 `{{`、不认识的标签），就先补 `tools/prototype-preview/dc-preview.js`，直到通过，再往下走。不要提交没通过的同步。
5. `git diff --stat prototype/` 看哪些画板变了，逐条对照设计文档。不符合文档的，列给人，改原型；文档里没有的，进「待人处理」，问人要不要写进文档。不要为了迁就原型去改文档。做完的「原型待改」条目标完成。
6. 按 `AGENTS.md`「收工前必须做的事」更新文档，提交，推送，按上面的模板开 PR。

同步改了「墨格」的 token 时，`apps/desktop/src/styles/tokens.css` 要跟着改。它由测试逐项比对原型，没跟上时 `pnpm test` 和 CI 会报出来。

本地会话只需 `git pull` 拿到最新的 `prototype/`，包括截图。

## 质量关

| 关 | 守什么 | 什么时候跑 | 谁看结果 |
| --- | --- | --- | --- |
| `pnpm check` | 格式、lint、类型、全部测试、前端构建 | 提交前；CI | CI 不过不合并 |
| 类型绑定一致 | 改了内核类型跑了 `pnpm bindings` | CI | 同上 |
| token 测试 | `tokens.css` 与原型的「墨格」逐项一致 | `pnpm test`；CI | 同上 |
| `check.js` | 原型能渲染，预览器认得所有写法 | 同步时；CI | 同上 |
| 示例数据跟上原型 | 原型变了，示例数据有没有跟上 | `pnpm workflow`；CI 留警告 | Agent 跟上后 `pnpm workflow accept` |
| `pnpm screens --compare` | 界面和原型长得一样 | 实现或改了页面后 | Agent 看拼图，差异写进 PR |
| `pnpm screens --snapshot` | 真实数据下没有报错、错位 | 改了内核或页面后 | Agent |
| `pnpm window-shot` | 窗口外壳：红黄绿按钮、工具栏对齐 | 改了 `tauri.conf.json` 或工具栏后 | Agent，拿不准再请人 |
| 人验收 | 用起来对不对 | 每轮末 | 人 |

## 工具

- **`pnpm workflow`**（`tools/workflow/status.mjs`）：一条命令看卡在哪。`--fetch` 先拉远端；`accept <画板…>` 记下示例数据已对齐的画板版本，记在 `apps/desktop/src/ipc/fixtures/prototype-sync.json`（按画板文件的哈希比，画板文件一变就算落后，哪怕只改了样式，看过没影响也 accept）；`--ci` 给 CI 用。
- **`pnpm screens --compare [画板…]`**：在本机重渲原型、截应用，逐张写出「原型 · 应用 · 差异标红」三栏拼图到 `apps/desktop/screens/compare-<画板>.png`，打印差异像素占比。占比是相对信号：侧栏宽度差约 10px（滚动条预留）会让整片内容错开，所以只看变化、看拼图，不设阈值。
- **`pnpm window-shot`**：找到方寸的窗口，提到前台，用 `screencapture` 按窗口截图，写出整窗图、左上角放大 4 倍图，并报出关闭按钮中心离工具栏按钮中心（19.25pt）差多少 pt。`--launch` 自己起 `pnpm dev`。第一次要给运行它的终端（或 VS Code）「屏幕录制」权限。

## 复盘

工作流本身也按「发现问题 → 改进 → 记录」迭代。

- **记摩擦**：谁遇到流程上的卡点（等人传话、重复劳动、返工、缺工具、规则互相打架），就在下面「摩擦记录」加一条 `- [ ] 日期 现象：谁卡住了，耽误了什么`。这是收工清单的一步。
- **什么时候复盘**：摩擦攒到 5 条（`pnpm workflow` 会提醒），或一个里程碑结束，或人说「复盘工作流」。
- **怎么复盘**：把摩擦归类，每类出一个改进项进 BACKLOG「工作流」（W-xx），能做的当场做。做完在「改进记录」加一行，对应的摩擦勾掉并注明 W 编号。
- **看什么**：一轮里人要介入几次、交接等了多久、同一件事返工几轮。
- **原则**：能写成脚本或 CI 的，不写成要人记住的规则。规则变了，先改这份文档，再改 `AGENTS.md` 里的指针。
