# 方寸 Fangcun：Agent 环境管理器 · 产品设计方案

> v0.6 · 2026-11-14 · 第 6 节是界面的要求，原型按它画，2026-11-14 核对过没有已知不一致；第 9 节的十四件待定事项已全部确认
> 产品名「方寸 Fangcun」，寓意「方寸之间，上下文井然」。

---

## 1. 结论先行

**一句话定位**：方寸是 Agent 上下文的「包管理器 + 环境管理器」，配一个好用的 Mac 桌面界面。它之于 Skills、MCP、指令文件，相当于 uv 或 mise 之于 Python 依赖与运行时。

**三个核心主张**

1. **Agent 读取的目录是构建产物，不是源。** `.claude/skills`、`.mcp.json`、`CLAUDE.md` 这些位置今天被人手工编辑、到处复制。方寸把它们降级为「由唯一来源生成的输出」。
2. **以项目为中心，而不是以资产库为中心。** 每个项目声明自己需要什么、锁定到哪个版本。全局层尽量薄。
3. **先看见，再管理。** 任何时刻都能回答「这个项目里的 Agent 此刻到底加载了什么、花了多少上下文、谁覆盖了谁」。

**MVP 是一个闭环**：看见 → 收编 → 声明 → 同步 → 更新。覆盖 Skills、MCP、指令文件三类资产，首批完整支持 Claude Code 与 Codex。

**关于命名**：业界说 harness 多指 Agent 运行时本身，例如 Claude Code、Codex。你描述的是运行时之上「可配置、可移植的那一层」。本文把它叫做 **Agent 环境**（项目级的整体）和 **上下文资产**（其中的每一件）。「project harness」作为口语别名保留。

## 2. 痛点深挖

### 2.1 你的机器就是证据

写方案前我只读扫描了本机，结果如下。

| 观察 | 事实 |
|---|---|
| Agent 工具数量 | 主目录下有 7 个工具的配置目录：Claude Code、Codex、Cursor、Gemini、opencode、Copilot、Windsurf。项目里还出现了 Trae。 |
| 同一 skill 的副本 | `project-harness` 在 5 个项目里各有一份。4 份内容相同，`evals_studio/.trae` 里那份已经分叉。 |
| 没有唯一来源 | `luyao-skills`、`my-skills`、`agent-skill`、`harness` 四个仓库里存放着内容相同的 skill。哪个是正本无从判断。 |
| 各工具分发不一致 | `~/.agents/skills` 有 31 个 skill。Claude Code 只链接了其中 16 个，Windsurf 有 20 个，Codex 有 3 个。 |
| 全局污染 | 本次会话开在一个空目录里，16 个飞书 skill 的描述仍全部进入了上下文。 |
| 版本停滞 | 全局锁文件最后修改于 7 月 5 日，而 skills 目录 11 月 11 日还在变动。锁与实际已脱节。 |
| MCP 配置分散 | 至少四处各自为政：`~/.claude.json`、`~/.codex/config.toml`、`~/.gemini/settings.json`、opencode 配置。 |

### 2.2 你提出的痛点

| 痛点 | 本质 |
|---|---|
| 不同项目要求不同的资产与版本 | 缺少项目级的需求声明与版本锁定 |
| 用户级与项目级冲突、无效占据上下文 | 作用域只有「全局 / 项目」两档，且生效结果不可见 |
| 版本经常得不到更新 | 资产没有来源记录，更新没有入口也没有提醒 |
| 一份 skill 复制得到处都是 | 没有唯一来源，复制是唯一的分发手段 |

### 2.3 你还没提到、但同样要命的痛点

1. **生效上下文不可见。** 托管层、用户层、项目层、本地层、插件层、子目录指令层层叠加，每个工具的优先级规则还不一样。没有人能一眼说出「最终生效的是什么」。
2. **上下文预算税。** 每个 skill 的名称与描述常驻上下文，每个 MCP 服务的工具定义也要占位，指令文件全文加载。全局装一个，所有项目都缴税。
3. **多工具碎片化。** 指令文件有 `CLAUDE.md`、`AGENTS.md`、`GEMINI.md`。MCP 配置有 JSON 也有 TOML。同一份意图要维护 N 种格式。
4. **原地修改无法回流。** Agent 工作时经常顺手改进项目里的 skill 副本。这些改进留在副本里，永远回不到来源，也到不了其他项目。
5. **供应链与信任。** Skill 带脚本，hook 执行任意命令，MCP 服务拿着你的凭据运行。上游一次静默更新就能改变 Agent 行为。
6. **密钥裸奔。** MCP 配置里的 API Key 以明文存在，随复制扩散，偶尔还被提交进 git。
7. **不可复现。** 新同事、新电脑、git worktree、云端或 CI 里的 Agent，都拿不到和你一样的环境。「在我的 Agent 上是好的」。
8. **隐式依赖。** Skill 依赖某个 CLI、某个 MCP 服务、某个环境变量，却从不声明。缺了就静默失效。
9. **个人与团队混在一起。** 哪些该提交给团队、哪些只是个人偏好，现有机制没有清晰的分层。
10. **只进不出。** 没有使用数据，不知道哪些 skill 从未被触发。资产只增不减，越积越乱。
11. **无法回滚与试验。** 改了一个 skill 效果变差，没有后悔药，也没法对比。
12. **作用域太粗。** 真实需求是「我所有前端项目」「这个客户的项目」「工作与个人」。全局与项目两档表达不了。

### 2.4 五个根因

所有痛点可以归到五个根因，产品的五个支柱一一对应。

| 根因 | 对应支柱 |
|---|---|
| A. 没有唯一来源 | 资产库 |
| B. 项目需求没有声明 | 项目清单与锁 |
| C. 生效结果不可见 | 生效上下文视图 |
| D. 目标格式碎片化 | 适配器与物化 |
| E. 没有生命周期 | 更新、回滚、回流 |

这其实是一个被解决过很多次的问题。Python 从全局 site-packages 走到 virtualenv 加锁文件。Node 从全局安装走到 `package.json`。Agent 上下文今天正处在「全局 site-packages」阶段。

## 3. 现状与竞品

以下判断基于各项目的自述页面，我没有逐一试用。这个领域每月都在变，立项前建议实测前三名。

| 类别 | 代表 | 解决了什么 | 留下的空白 |
|---|---|---|---|
| Skill 命令行 | [vercel-labs/skills](https://github.com/vercel-labs/skills) | 安装、软链到多个工具、全局锁与项目锁 | 只管 skill。锁里只有哈希没有版本语义。没有可见性。[删除后锁残留](https://github.com/renovatebot/renovate/discussions/41841)等粗糙处仍在 |
| Skill 桌面库 | [skills-manage](https://github.com/zhaikong/skills-manage)、[Skills Manager](https://skillsmanager.dev/)、[Skill Desktop](https://skill-desktop-labs.github.io/skill-desktop-landing/)、[Agent Desk](https://agentdesk.sh/) | 一个库分发到几十个工具 | 以库为中心，本质是「全局分发器」。项目级版本锁定与生效视图薄弱 |
| MCP 管理器 | [MCP Linker](https://mcp-linker.milisp.dev/)、[Claude Code Tool Manager](https://github.com/tylergraydev/claude-code-tool-manager)、[mTarsier](https://mtarsier.com/) | 多客户端 MCP 配置同步，部分支持按项目指派 | 与 skill、指令割裂。密钥与复现不是重点 |
| 锁与体检命令行 | [skillock](https://github.com/quantz8a/skillock)、[agent-skills-cli](https://github.com/Karanjot786/agent-skills-cli) | 锁文件、token 预算、冲突检测 | 只有命令行，各管一段，没有闭环 |
| 原生机制 | Claude Code 插件与市场 | 打包分发、按项目启用 | 只在单一工具内有效 |

**空白在哪里**：现有产品几乎都在回答「怎么把一个库同步到 N 个工具」。没有产品把这四件事合在一起：

- 以项目为中心的声明与逐项目版本锁定
- 跨资产类型统一管理：skill、MCP、指令
- 生效上下文的透视与预算
- 副本修改的回流

**必须正视的事实**：赛道已经拥挤。方寸的差异不能靠功能清单，要靠「项目中心的闭环」和体验质量。[agentskills.io 的实现指南](https://agentskills.io/client-implementation/adding-skills-support)已约定项目级覆盖用户级并建议提示用户，说明「遮蔽可见性」是公认需求但尚无好的界面。

## 4. 核心理念与概念模型

### 4.1 一条流水线

```
来源 Source ──▶ 资产库 Library ──▶ 清单 + 锁 ──▶ 物化 Sync ──▶ 生效视图 X-Ray
(git/本地/市场)   (唯一正本，带版本)   (项目声明)     (写入各工具原生位置)   (看见结果)
                        ▲                                  │
                        └────────── 回流 Promote ◀──────────┘
                                 (副本被改，决定去留)
```

### 4.2 七个概念

| 概念 | 含义 | 类比 |
|---|---|---|
| **资产 Asset** | 一件可被 Agent 读取的东西。MVP 含三类：Skill、MCP 服务、指令文件 | 包 |
| **来源 Source** | 资产的出处：git 仓库、本地开发目录、公开市场 | 注册表 |
| **资产库 Library** | 本机唯一正本，按内容寻址存储，保留每个版本 | 包缓存 |
| **套装 Bundle** | 一组常一起用的资产，起个名字给多个项目复用，例如「飞书办公」「前端基线」 | 依赖组 |
| **清单 Manifest** | 项目根目录的 `fangcun.toml`，声明目标工具、资产、版本约束 | `package.json` |
| **锁 Lock** | `fangcun.lock`，记录解析出的确切提交与内容哈希 | 锁文件 |
| **物化 Sync** | 把解析结果写进各工具的原生位置，并记录哪些文件归方寸管 | 安装 |

### 4.3 作用域：从两档变四层

```
全局基线   尽量薄，只放真正每个项目都要的
   ▼
套装       按项目类型、客户、场景复用
   ▼
项目清单   提交到 git，团队共享
   ▼
个人覆盖   fangcun.local.toml，不提交，只属于你
```

下层覆盖上层。覆盖关系在界面里永远可见，不靠记忆。

这是方寸声明的规则。落到工具时，同名项谁生效按工具自己的规则，生效上下文视图如实显示，不替工具改写：

- Claude Code 的同名 skill 是上层优先（官方文档：个人盖过项目），与这里相反；同名 MCP 是个人 > 项目 > 全局，整条取用。
- Codex 的同名 skill 不合并，两份都加载；同名 MCP 项目层赢，按字段合并。

工具规则与方寸相反时，物化不自动移动上层的同名项：全局目录是所有项目共用的，移走它，没覆盖它的项目也读不到了。方寸把这种情况标为「同名冲突」，给出「转成套装」「从全局移除」两个动作，都先出变更计划，列出受影响的项目，由人决定。

### 4.4 版本是什么

Skill 规范本身没有版本字段。方寸定义版本为「来源提交 + 内容哈希」。有 git 标签就显示标签，没有就显示日期与短哈希。每项资产有两种跟随方式：

- **固定 Pin**：锁死在某个版本，只有手动才变。
- **跟随 Track**：跟着某个分支，有新版本时提醒，确认后才更新。

### 4.5 你的例子怎么解

项目 A 要 Skill A v1、Skill B v1。项目 B 要 Skill B v2、Skill C v1。

- 资产库里 Skill B 的 v1 与 v2 并存，各一份。
- 项目 A 的清单固定 B 到 v1，项目 B 固定到 v2。各自物化进自己的项目目录。
- 全局层不安装 B，于是不存在覆盖干扰。
- 上游出 v3 时，活动页的待处理里出现一条「可更新」，列出这两个项目，各自决定是否升级。

### 4.6 六条设计原则

1. **不发明运行时。** 只写各工具的原生位置。卸载方寸后一切照常工作。
2. **文件即真相。** 清单与锁是纯文本，可读、可提交、可审查。界面只是它们的编辑器。
3. **预览先于写入。** 任何落盘动作先出变更计划，确认后才执行。
4. **一切可撤销。** 每次同步都是一个快照，可一键回退。
5. **只动自己的东西。** 记录所有权。共享文件按键合并，绝不整文件覆盖。
6. **本地优先。** 不需要账号，默认不上传任何数据。

## 5. MVP 核心功能

MVP 的范围是六项能力。每项都直接对应第 2 节的痛点。

### F1 全盘体检与收编

- 扫描主目录与你登记的项目目录，识别所有工具的 skill、MCP、指令文件。
- 按内容哈希归并：哪些是同一份的副本、哪些已经分叉、哪些来源未知。
- 输出体检报告，每条发现配一个可撤销的一键动作。
- 「收编」把选中的资产移入资产库，原位置替换为受管链接，事前自动备份。

**验收**：从安装到看到体检报告不超过两分钟，全程零配置。在你的机器上应能直接报出「project-harness 有 5 份副本，其中 1 份已分叉」。

### F2 资产库

- 按内容寻址存储，多版本并存。
- 三种来源：git 仓库、本地开发目录、公开 skill 市场。
- 本地开发目录是「活链接」：你在自己的 skill 仓库里改，登记为开发模式的项目立即可见。
- 每项资产显示：来源、版本历史、被哪些项目使用、预估 token 成本、是否含脚本。
- 按类型与来源筛选，来源按本地开发、GitHub、npm、待收编分组。

**验收**：同一 skill 在本机只有一份正本。任一资产都能回答「从哪来、谁在用、哪个版本」。

### F3 项目环境：清单与锁

- 登记项目后生成 `fangcun.toml` 与 `fangcun.lock`。
- 声明目标工具、套装、资产与版本约束、物化方式。
- `fangcun.local.toml` 承载个人覆盖，自动加入 `.gitignore`。
- 能从现状反推：对已有项目，直接把当前目录里的资产反向生成清单。
- 能导入 `skills-lock.json`，与现有命令行生态互通。

**验收**：新机器上克隆仓库，一条命令或一次点击即可还原完全相同的环境。

### F4 物化同步与漂移处理

- 先出变更计划，列出将新增、修改、删除的每个文件。
- 两种物化方式，按项目选择：
  - **链接**：项目目录里是指向资产库的软链，零重复，适合个人项目。
  - **入库**：实体文件提交进仓库，同事与云端 Agent 无需安装方寸，适合团队项目。
- 多工具去重：实体只放一份在 `.agents/skills`，其他工具目录用相对软链指过去。
- 文件监听发现受管副本被修改时，给三个选择：**回流**到来源、**丢弃**修改、**分叉**为项目专属。

**验收**：同步不触碰任何非受管文件。Agent 在项目里改了 skill，五秒内出现漂移提示。

### F5 生效上下文视图

这是方寸的招牌界面，也是与竞品最大的区别。

- 按「项目 × 工具」展示 Agent 实际加载的全部内容，标明每一项来自哪一层。
- 标出被覆盖、重名冲突、重复加载、来源未知。
- 上下文预算条：常驻成本与按需成本分开估算，并标明是估算值。对照的项目预算写在 `fangcun.toml`，没写时 20k（7.4）。
- MCP 的常驻是工具定义，要启动服务才读得到。M0 不启动任何进程，MCP 标「未估算」，预算条的 MCP 段为 0，旁边写「MCP N 个未估算」。M1 提供显式的「试启动并测量」动作，结果缓存。
- 同名项谁生效按工具的真实规则（4.3）。
- 就地操作：从全局降级为按项目、在本项目停用、查看覆盖它的是谁。
- 每一项都能看到：为什么是这个状态、在哪一层声明、占多少常驻、写入了哪些文件、最近活动。
- 插件、hook、子代理、斜杠命令在 MVP 里只看不管：逐行展示，不提供操作，不计入预算。

**验收**：对任一项目，十秒内回答「加载了什么、谁覆盖了谁、常驻占多少」。

### F6 更新、回滚与密钥

- 更新：列出有新版本的资产与受影响项目，展示差异，脚本与命令变更高亮警示。不单独设「更新中心」页面，入口在活动页的待处理，处理在项目页检查器。
- 可逐项目升级，也可批量升级。每次同步留快照，一键回滚。
- MCP 密钥存入 macOS 钥匙串。提交进仓库的配置只含环境变量引用，明文只落在不提交的本地配置里。
- 体检会报告「已提交文件里有明文密钥」。

**验收**：升级前必能看到差异。回滚后磁盘状态与上一快照逐字节一致。

### 配套：命令行

桌面应用与命令行共用同一个内核。命令行让 CI、云端 Agent、worktree 无需界面也能还原环境。

```bash
fangcun doctor                # 只读体检
fangcun init --from-existing  # 登记项目，从目录现状反推清单与锁
fangcun status                # 当前项目的同步状态与漂移
fangcun add <资产>             # 加入清单
fangcun adopt <资产>           # 收编进资产库
fangcun lock                  # 重新解析清单，更新锁
fangcun sync                  # 按清单与锁物化
fangcun sync --frozen         # CI 用：锁与清单不一致就失败
fangcun update [资产]          # 检查并升级。--dry-run 只看差异，--projects 指定项目
fangcun rollback <快照>        # 回滚到某个快照
fangcun log                   # 查看活动记录
fangcun why <资产>             # 解释它为何生效、来自哪一层。--global 看全局层
```

活动页的检查器会给每条记录附上对应的命令，界面能做的事命令行都能做。

### MVP 明确不做

- 不管理会话状态类资产，例如记忆、任务进度文档。它们是「演化中的状态」而非「配置」，机制不同。
- 不做自建市场，不做账号体系，不做云同步。
- 不代理或拦截 Agent 运行，不做 MCP 网关。
- 不安装 CLI 依赖。只在后续版本做「依赖是否就绪」的检查。
- 不做 skill 质量评测。

## 6. 关键界面与体验流程

本节是界面的要求。高保真原型按本节画，两者不一致时以本节为准，改原型。原型有七张画板：设计系统「墨格」、项目页、体检报告、资产库、套装、全局、活动，源文件在仓库的 `prototype/`。最近一次核对是 2026-11-14，画布版本 1794656963-e22c，七张画板逐张对照本节。对照出的五处（BACKLOG D-24 至 D-28）当天已改完，没有已知不一致。

本节早期的写法是对照原型整理出来的（11-13、11-14 的导出件已删除，可从 git 历史取回）。2026-11-14 起顺序反过来：先改本节并经人确认，再改原型，再实现。

线框图与原型里的数字、名称都是示意，不全是实测结果。各画板的示例数据之间有几处对不上，各小节照各自的画板写。

### 6.1 形态

- **主窗口**：自上而下是整窗工具栏，下面是侧栏、列表、检查器三栏。
- **菜单栏常驻图标**：显示漂移与可更新的角标，可快速跳到项目。角标数字与活动页的待处理数一致。
- **命令面板** `⌘K`：搜索资产、项目、动作。键盘优先。
- **命令行** `fangcun`：见上节。

**窗口骨架**，所有页面共用：

- **整窗工具栏**：高 40px，贯穿窗口顶部。从左到右依次是窗口按钮、后退与前进、侧栏开关。窗口控件只出现在这里，侧栏折叠与否都不影响左上角。
- **侧栏**：顶部是「方寸」标识，下面五个导航项：**项目**、**资产库**、**套装**、**全局**、**活动**。前四项旁的灰色数字是数量，「活动」旁的橙色数字是待处理数。项目页下方列出已登记项目及其状态点。M0 没有登记，列的是近 30 天会话记录里出现过的工作目录，往上归到 git 根目录（主目录本身、临时目录、主目录下的点目录不算），分组标题写「近 30 天的项目」。M1 起分两组：上面是「已登记项目」，下面「近 30 天的项目」只列还没登记的目录，标「未登记」。底部固定「重新体检」，下面一行小字「本地优先 · 零遥测」。侧栏可折叠为 56px 宽的图标栏，此时只保留导航图标。
- **列表与检查器**：选中列表中的一行，右侧检查器显示详情。检查器右上角有 × 关闭按钮，关闭后列表占满宽度；再点任意一行即重新打开。
- **分栏独立滚动**：窗口固定为一屏高，侧栏、列表、检查器各自滚动，滚动一栏时其他栏不动。窗口窄于 900px 时，各栏改为上下堆叠，整页滚动。

**检查器统一结构**：项目页、资产库、体检报告、全局、活动五处的详情面板用同一套结构，依次是类型小标签、名称、状态徽标、一句说明、字段表、若干分区、操作。分区标题统一用 11px 灰色小字，内容超出时出现细滚动条。

### 6.2 首次启动：体检报告

体检报告沿用主窗口骨架，主体是「发现列表 + 检查器」两栏，不另做弹窗。

```
● ● ●  ←  →  ▣
──────────────┬────────────────────────────────────────────────────────────
 方寸          │ 体检报告  ● 只读扫描完成，未改动任何文件     [稍后处理] [进入项目]
 项目       6  │ 处理进度 0 / 5   扫描了 7 个工具、61 个项目目录   重复副本 4
 资产库    38  │ ▭▭▭▭▭
 套装       3  ├───────────────────────────────────────┬────────────────────
 全局      31  │ 类别      发现                     状态   │ 体检发现             ×
 活动       2  │ ● 重复    project-harness 有 5 份…  待处理 │ project-harness 有 5 份副本
               │ ● 重复    4 个仓库存放着相同的 skill 待处理 │ ● 重复
               │ ● 全局税  16 个飞书 skill 进了每个项目 待处理 │ 按内容哈希归并……
               │ ● 不一致  31 个全局 skill 分发不齐  待处理 │ 涉及的位置
               │ ● 脱节    全局锁文件与目录不一致    待处理 │  agent-lab/…   4d9b1eb  相同
               │ ● 密钥    检查已提交文件中的明文密钥 尚未扫描│  evals_studio/… e81c55a 已分叉
 重新体检       │                                         │ [收编到资产库]
 本地优先·零遥测 │                                         │
```

- 概要条与项目页的预算条同一样式。每处理一项发现，进度条点亮一段。
- 处理完的发现划线并标「已处理」，检查器显示「已处理 · 已留快照」和撤销，然后自动跳到下一条。
- 第一屏就给出价值，不要求先建库、先配置。

**页头**：项目名与路径、目标工具分段控件、漂移徽标、命令面板入口、「同步 · N」主按钮。切换目标工具后，列表只显示该工具实际加载的内容，例如 Codex 不读取 `CLAUDE.md`。

**预算条**：指令、Skill、MCP 三段，同一色相、三档明度，对照项目预算显示，始终标明「估算值」。项目预算取 `fangcun.toml` 的 `budget`，没写时 20k。MCP 没测量过时，该段为 0，旁边写「MCP N 个未估算」。

**生效上下文列表**：

- 按指令、Skills、MCP 分组。每行四列：名称与版本、层级刻度与作用层、状态、常驻估算。
- 最后一组是「其他加载项」，带「只看不管」标签，逐行列出插件、Hook、斜杠命令、子代理，列与上方资产对齐。这些行不可操作，不计入预算，未发现的类型用一行小字说明。

**检查器**：

1. 状态专属操作区，只在需要时出现：
   - 漂移：差异片段，回流、丢弃、分叉三选一，预览后应用。
   - 可更新：版本差异，脚本变更标红。同一资产在其他项目也可更新时，列出受影响的项目供勾选，一起加入同步计划。
   - 全局税：在本项目停用，或改为套装。
   - 被覆盖：跳到覆盖它的项。工具规则是上层优先、被遮蔽的是项目层这一份时（例如 Claude Code 的 skill），另给「转成套装」「从全局移除」，处理全局那一份。
   - 来源未知：去资产库收编。
2. **为什么是这个状态**：用两句白话解释，下方附命令行的对应写法 `fangcun why <资产>`。
3. **在哪一层声明 · 谁覆盖谁**：全局、套装、项目、个人四行。生效的那层用绿底，被遮蔽的划线，停用的用橙色。工具规则与「下层覆盖上层」相反时，下面一行小字：「这个工具同名时上层优先，与『下层覆盖上层』相反」。
4. **上下文占用**：占本项目常驻的百分比，超过 30% 显示为橙色。
5. **写入了哪些文件**：实际物化的路径与软链指向，以及按键合并的配置项。
6. **最近活动**：这一项的时间线。

**清单页签**：顶部一句话说明清单的用途，下面三张文件卡可切换：

| 文件 | 角色 | 提交 |
|---|---|---|
| `fangcun.toml` | 项目清单 | 提交到 git |
| `fangcun.lock` | 版本锁，自动生成 | 提交 |
| `fangcun.local.toml` | 个人覆盖 | 不提交 |

默认是「结构化」视图，按区块用表格展示：项目设置，Skills（来源与版本策略，标注哪项来自套装），MCP 服务（启动命令与密钥位置），指令文件（正本与镜像）。可以切换到「源文件」视图，带行号，长行自动折行。界面上的改动会同步出现在两种视图里。

**历史页签**：快照列表，每条可「回滚到此」，当前磁盘状态有标记。

### 6.4 资产库

- **列表**：每行显示名称与来源、类型、使用中的项目数、状态。
- **筛选**：类型芯片（全部、Skill、MCP、指令）加一个「来源」下拉框，两者可以叠加。下拉框按本地开发、GitHub、npm、待收编分组，每项带资产数量；来源再多也只占一个控件。筛选结果为空时提供「清除筛选」。
- **详情**：与检查器同一结构。
  - 字段表：来源、正本、常驻、使用中、含脚本。含脚本时标红。
  - 版本：锁定中的版本用绿底标出。
  - 被哪些项目使用：每个项目的版本策略与物化方式。
  - 最近活动。
  - 来源未知的资产在底部提供「收编到资产库」。

### 6.5 套装

**套装**是一组常一起用的资产，起个名字给多个项目复用，例如「工程基线」「飞书办公」。它介于全局和项目之间：比装进全局更精准，不会给无关项目增加上下文负担；比逐个项目添加更省事。

- **左栏**：顶部是「新建套装」按钮，下面是「全部套装 · N」与套装列表。每个条目两行：名称与常驻估算、资产数与项目数。左栏可以折叠为首字方块组成的窄条，折叠后仍可切换和新建。
- **右侧详情**：
  - 清单写法 `bundles = ["<名称>"]`。
  - 包含的资产表：类型、版本策略、常驻。
  - 「哪些项目使用它」复选列表：勾选变化时标出「将加入」「将移除」，并给出常驻变化，确认后预览变更计划。

### 6.6 全局：瘦身

**全局**是四层作用域的最上层，这里的每一项都会进入每个项目的上下文。页头的副标题说明了这一页的目的：「每个项目都会加载这一层，越薄越好」。它把全局层的每一项按常驻成本排开，标出近 30 天有几个项目真正用到，再让你把用得少的转成套装或移除。

**页头**：

- 第一行是标题「全局」、副标题、目标工具切换。切换后列表与预算只算该工具实际加载的内容。
- 第二行是预算：「给每个项目带来常驻 11.8k / 项目预算 20k · 估算值」，右边是指令、Skill、MCP 三段的数值，下面是与项目页同一样式的三色预算条。
- 瘦身之后，预算旁多一句「较瘦身前 −6.4k」。

**筛选与快速选择**：

- 类型芯片：全部、Skill、MCP、指令，每个带当前工具下的数量。
- 「快速选择」后面有两个按钮：「很少用到 · N」和「从未使用 · N」。点一下就勾选对应的行，不改变筛选。
  - 「很少用到」选中状态为「建议转套装」的行。
  - 「从未使用」选中状态为「从未使用」的行，以及「被覆盖」「同名冲突」的行。

**列表**：

- 不分组，按常驻估算从高到低排列。全局的每一项对每个项目成本相同，所以这个顺序就是瘦身收益的顺序。
- 行首是复选框，表头的复选框全选当前列表。
- 五列：名称与位置、类型、用到它的项目、状态、常驻。
- 名称下面一行小字是位置，用等宽字体，例如 `~/.agents/skills/lark-*` 或 `~/.claude.json · mcpServers.context7`。
- 来源相同的一组资产合并成一行，名称后带数量标记，例如「lark-* 飞书 skill · 16 项」。
- 「用到它的项目」是一小段进度条加「1 / 6」。用到的项目不超过 2 个时进度条为橙色，更多时为绿色。指令文件没有「触发」可统计，这一列写「—」。
- 被项目层覆盖的行，名称划线。
- 列表末尾有一行小字。它先说明别的工具还加载了什么，例如「另有 2 项只被 Codex 加载，切换工具查看」。然后说明数据来源：「『用到』依据本机会话记录近 30 天的触发情况，不上传」。
- 筛选结果为空时显示「这一类在当前工具的全局层里没有资产」和「清除筛选」。

**状态**：按「近 30 天有多少项目用到」给出，直接对应建议的动作。

| 状态 | 颜色 | 含义 | 建议 |
|---|---|---|---|
| 建议转套装 | 蓝 | 只有一两个项目用到 | 转成套装 |
| 从未使用 | 橙 | 近 30 天没有项目触发 | 从全局移除 |
| 被覆盖 N 处 | 灰 | 有项目在项目层放了同名项，按工具规则项目层生效，把它遮蔽了（例如 MCP） | 从全局移除 |
| 同名冲突 N 处 | 灰 | 有项目在项目层放了同名项，但按工具规则全局这一份生效（Claude Code 的 skill），或两份都加载（Codex 的 skill） | 转成套装或从全局移除 |
| 全文加载 | 灰 | 指令文件，每个项目的每次会话都全文加载，没有「触发」可统计 | 只放每个项目都需要的约定 |
| 来源未知 | 紫 | 内容哈希与任何来源都不匹配 | 先去资产库收编 |
| 常用、多数项目在用、每个项目都用 | 绿 | 一半以上的项目用到 | 留在全局 |

**批量操作条**：勾选任意一行后，列表底部出现一条：「已选 18 项 · 每个项目常驻 −7.0k（估算）」，后面是「取消选择」「从全局移除…」「转成套装…」。

**检查器**：沿用统一结构。

- 类型小标签写类型、数量和层，例如「Skill · 16 项 · 全局层」。下面是名称、状态徽标、一句说明。
- 字段表：位置、来源、版本、常驻、用到它、含脚本。
  - 常驻写成「6.4k / 每个项目（估算）」，达到 3k 时显示为橙色。
  - 来源未知时来源一栏为紫色。
  - 含脚本或带启动命令时标红。
- **建议**：一段话说明该留还是该走，并给出数字，例如「只有 client-acme 用到。转成套装后，其余 5 个项目每个省下 6.4k 常驻」。
  - 下面按情况给按钮：「转成套装…」「从全局移除…」，或「去资产库收编」。建议留在全局的项没有按钮。
  - 最下面附命令行的对应写法 `fangcun why <资产> --global`。
- **用到它的项目 · 近 30 天**：六个项目各一行，标记为「用到」「未用到」「被项目层覆盖」或「同名冲突」。指令文件不显示这一分区。
- **分发到哪些工具**：
  - Skill 列出 Claude Code、Codex、Windsurf 三行，各写目标路径和「已链接」或「未分发」。
  - MCP 与指令文件列出所在工具的配置路径，标「按键合并」或「全文加载」，其他工具标「未配置」。
- **最近活动**：末尾有链接「在『活动』里查看全部」。

**变更计划**：「转成套装…」和「从全局移除…」都先弹出变更计划，版式与同步的变更计划相同。

```

│                                                                        │

│    ☐ blog-site      ☐ notes-kit    ☑ client-acme                       │
```

- 标题是「把 N 项转成套装」或「从全局层移除 N 项」。副标题固定为「预览先于写入。应用前自动快照，可在『活动』一键回滚。资产库里的正本不受影响」。
- 转成套装时多两样东西：
  - **套装名称**：可以改。默认名按所选内容给出，例如选中飞书 skill 时是「飞书办公」。旁边显示清单写法 `bundles = ["飞书办公"]`。
  - **哪些项目需要它**：六个项目的复选列表，已按「用到」预选。
  - 只勾选了一个项目时，多一个选项：不建套装，直接写进那个项目的清单。选了它，计划里就没有新建套装文件那一行。
- 计划里的三类变更：
  - `+` 新建套装文件 `~/.fangcun/bundles/<名称>.toml`。
  - `~` 所勾选项目的 `fangcun.toml`，在 bundles 里加入这个套装。
  - `−` 当前工具全局目录里的链接或配置项。转成套装时注明「移出全局层，已备份」，从全局移除时注明「移出全局层，资产库保留正本」。
- 底部一句话给出结果，例如「5 个项目每个常驻 −6.4k（估算）。不会触碰其他任何文件」。

**应用之后**：

- 被处理的行从列表消失，预算条变短，页头出现「较瘦身前 −6.4k」。侧栏「全局」与「套装」旁的数字同步变化。
- 提示条写明结果并带撤销：
  - 转成套装：「已创建套装『飞书办公』，写入 1 个项目清单 · 已留快照」，另有「去套装页」链接。
  - 从全局移除：「已从全局层移除 5 项 · 已留快照」。
- 点撤销后提示「已撤销，恢复到上一快照」。

**其他页面上的相关入口**：三个按钮与瘦身有关，做的是同一件事或它的局部版本。

| 入口 | 按钮 | 做的事 |
|---|---|---|
| 体检报告的「全局税」发现 | 创建套装「飞书办公」 | 转成套装，在体检里就地完成 |
| 项目页检查器 | 改为套装「飞书办公」 | 转成套装，从项目页发起 |
| 项目页检查器 | 在本项目停用 | 不动全局，只在这个项目的清单里写入停用 |

**没有全局清单**：全局层就是各工具的全局目录，首版不为它另设清单文件。值得在新机器上还原的东西，应该进套装或项目清单。

**阶段**：列表、预算、建议都不写文件，随 M0 提供。它们依赖的使用数据也在 M0 读取。转成套装与从全局移除属于 M1。

活动相关的界面有三处，它们是同一份记录的不同切面：

| 位置 | 范围 | 用途 |
|---|---|---|
| 检查器的「最近活动」 | 单个资产 | 看这一项经历过什么 |
| 项目页与全局页的「历史」页签 | 单个项目或全局层 | 在这个范围内回滚 |
| 活动页 | 所有项目与全局层 | 跨项目追溯、回滚，找到待处理的事 |

**页头**：标题「活动」、副标题、「项目」下拉框。下拉框列出「全部项目（N）」、每个已登记项目和「全局层」，选中某一项后控件变为强调色。

**筛选**：一排类型芯片，依次是全部、同步、漂移、升级、收编、回滚、体检、校验、密钥。

- 「升级」同时包含「可更新」的记录。
- 类型芯片与「项目」下拉框可以叠加。
- 筛选结果为空时显示「没有符合筛选的活动」和「清除筛选」。

**列表**：

- 五列：时间、类型、事件与项目、快照、状态。
- 每行两行文字。上面是事件标题，下面的小字是「项目 · 触发方」。
- 涉及一两个项目时写出项目名，更多时写成「evals_studio 等 5 个项目」，全局层的记录写「全局层」。
- 按天分组，新的在上。分组标题写成「今天 · 11-13」「昨天 · 11-12」「11-11 周二」。
- 列表末尾一行小字：「更早的记录保留在 `~/.fangcun/journal`，命令行可用 `fangcun log` 查看。」

**待处理**：

- 置顶的一组，标题是橙色的「待处理 · N」。行式与下面的时间线完全相同。
- 目前有两类：漂移（橙）和可更新（蓝）。
- 活动页不处理它们，只负责带你过去。选中后检查器给出跳转：漂移是「去处理漂移」，可更新是「查看差异」，都到项目页的检查器里完成。
- 侧栏「活动」旁的橙色数字是待处理总数，不受筛选影响。分组标题里的 N 是筛选后的数量。

**类型**：

| 类型 | 含义 | 示例 |
|---|---|---|
| 同步 | 按清单与锁物化，包括登记项目 | 同步 3 处变更；登记项目，生成清单与锁 |
| 漂移 | 受管副本被修改 | project-harness 的副本被修改 |
| 升级 | 资产换到新版本 | 升级 frontend-design v1.1.0 → v1.3.0 |
| 可更新 | 来源有新版本，等你确认 | tdd 上游有新提交 b7e9f0 |
| 收编 | 副本归并进资产库 | 收编 project-harness：5 份副本归并为 1 份正本 |
| 回滚 | 撤销某次写入 | 回滚到快照 #88 |
| 体检 | 只读扫描 | 首次体检：扫描 7 个工具、61 个项目目录 |
| 校验 | 在本机运行 `fangcun sync --frozen` 的结果 | 校验失败：锁与清单不一致 |
| 密钥 | 存入、替换、删除钥匙串条目。只记名称和位置，从不记值 | github-token 迁入钥匙串 |

「校验」只记录在本机运行的校验，例如提交前的钩子。远端 CI 的结果没有通道回到本机，留到 V2。

**状态**：

| 状态 | 颜色 | 含义 |
|---|---|---|
| 已应用 | 绿，回滚类记录用灰 | 已写入文件并留了快照 |
| 待处理 | 橙或蓝 | 等你决定，置顶显示 |
| 失败 | 红 | 没有写入，例如校验不通过 |
| 已回滚 | 灰，标题划线 | 这次写入后来被回滚了 |
| 已记录 | 灰 | 监听到的变化，没有写入任何文件 |
| 只读 | 灰 | 体检扫描 |

**触发方**有五种：桌面应用、命令行、文件监听、上游检查、首次启动。从终端运行 `fangcun` 产生的记录同样出现在这里。

**快照**：

- 快照按项目各自编号。示例里 evals_studio 到了 #127，client-acme 是 #41。
- 一次操作涉及多个项目时，活动页只有一条记录，每个项目各留一个快照。列表里显示第一个编号，检查器里写全，例如「#126 · #63」或「#125 等 5 个」。
- 没有写入文件的记录，快照一列显示「—」，检查器里写「无，未写入文件」。
- 快照和它的备份默认保留 30 天，并且每个项目至少保留最近 20 个，可在设置里调整。记录本身一直保留。快照过期后，这条记录的回滚按钮置灰并说明原因。

**检查器**：沿用统一结构。

- 类型小标签写类型和快照，例如「同步 · 快照 #127」。下面是标题、状态徽标、一句说明。
- 字段表：项目、时间、触发、快照。
- **写入了哪些文件**：这次实际执行的变更，写法与同步预览一致。没有快照的记录，这一分区的标题改为「涉及的文件」，只读或未改动的文件用 `=` 标记。
- **命令行**：做同一件事的命令和它的输出，例如 `fangcun sync` 与「3 处变更 · 快照 #127」。
- 操作区按记录的情况给出不同内容：

| 记录 | 操作区 |
|---|---|
| 已应用的写入 | 「回滚到此之前…」按钮 |
| 已回滚的写入 | 一句「这次变更已被回滚，磁盘状态与上一快照一致」 |
| 漂移 | 「去处理漂移」，跳到项目页 |
| 可更新 | 「查看差异」，跳到项目页 |
| 校验失败 | 「打开项目」 |
| 体检 | 「打开体检报告」 |
| 全局层的记录 | 「去全局页」 |
| 快照已过期 | 置灰的「回滚到此之前…」，下面一句原因：「快照 #1 已过期，备份已清理。快照默认保留 30 天，每个项目至少保留最近 20 个，可在设置里调整。记录仍在。」 |
| 密钥 | 一句「密钥记录不能回滚，钥匙串条目保持现状。要撤销，用『替换』或『删除』再记一条。」 |

**回滚预览**：点「回滚到此之前…」弹出，版式与同步的变更计划相同。

```
┌─ 把 evals_studio 回滚到快照 #126 ──────────────────────────────────┐
│  撤销「同步 3 处变更」。预览先于写入，只动这次变更写过的文件。     │
│                                                                    │
│  − .agents/skills/tdd      移除链接                                │
│  − .claude/skills/tdd      移除链接                                │
│  ~ .mcp.json               删除键 mcpServers.github，其余键不动    │
│                                                                    │
│  回滚本身也会留一个快照，可以再撤销。      [取消]  [回滚 ⌘↩]       │
└────────────────────────────────────────────────────────────────────┘
```

- 标题写明范围和目标快照。跨项目的记录写成「把 2 个项目回滚到快照 #125 · #62」。项目的第一条记录没有上一个快照，写成「回滚到登记前」或「回滚到收编前」。
- 下面列出逆向的变更计划。
- 有文件被后来的变更动过时（回滚规则第 6 条）：这些行标橙，说明改成「快照 #126 之后也改过这个文件」；计划上方一条橙色提示「N 个文件被后来的变更改过。先回滚『…』（快照 #126 · #63），再回滚这一条。不做自动合并」，带「查看那条记录」；「回滚」按钮置灰。先回滚了后面那条，再打开预览时提示消失。
- 应用后发生三件事：
  1. 列表顶部多一条「回滚」记录，带一个新快照。
  2. 原记录的状态变为「已回滚」，标题划线。
  3. 出现提示条「已回滚到快照 #126，磁盘状态逐字节一致」，带「撤销」和「好」。点撤销后提示「已撤销回滚」。

**回滚规则**：

1. 回滚执行的是那次变更的逆操作，只动那次变更写过的文件。
2. 回滚本身也留快照，所以可以再撤销。记录只增不删。
3. 跨项目的记录一起回滚。
4. 收编前、覆盖前的原文件都有备份，回滚时从备份还原。丢弃漂移修改也是一条写入记录，想找回被丢弃的修改，对它回滚即可。
5. 资产库里的正本不随回滚删除。例如回滚 skill-b 的升级后，v2.1.0 仍留在资产库。
6. 回滚较早的记录时，如果后来的变更也动过同一批文件，回滚预览里会标出这些文件，并要求先回滚后面的记录。不做自动合并。
7. 没有写入文件的记录不能回滚，包括待处理、失败、已记录、只读。密钥记录也不能回滚，钥匙串条目保持现状。

**没有「更新中心」页面**：可更新的入口就是这里的待处理项，处理在项目页检查器里完成。跨项目的批量升级也在检查器里做，勾选受影响的项目即可。

**阶段**：M0 只写方寸自己的 `~/.fangcun`，体检记录存进 `~/.fangcun/journal`，重启后和 `fangcun log` 都看得到。这里只有体检和「已记录」两类记录。回滚随 M1 开放。

检查器里的停用、升级等操作先加入同步计划，由「同步 · N」统一预览和应用。应用后出现提示条，并生成一个快照。

全局页的「转成套装」和「从全局移除」用的是同一种变更计划，见 6.6。变更涉及多个项目时，应用后每个受影响的范围各留一个快照，在活动页是同一条记录。

### 6.9 关键流程

1. **给项目加资产**：`⌘K` 搜索，回车加入，弹出变更计划，应用。全程不离开键盘。
2. **处理漂移**：点页头的漂移徽标，检查器定位到该资产，看差异，三选一。选「回流」时列出同样使用该资产的其他项目，逐个决定是否跟进。
3. **升级**：从活动页的待处理项点「查看差异」，或直接在项目页选中这一项，在检查器里看差异。脚本改动标红，审阅后加入同步计划，再应用。不满意就在「历史」或「活动」里回滚。
4. **全局瘦身**：「全局」页按常驻成本从高到低排列，并标出近 30 天有几个项目用到。点「很少用到」选中一批，再点「转成套装…」，在变更计划里确认套装名称和需要它的项目，应用。之后可以在套装页继续调整。
5. **追溯与回滚**：发现 Agent 行为变了，打开活动页，用「项目」下拉框筛到这个项目，找到可疑的那条记录，看它写入了哪些文件，点「回滚到此之前…」，预览后回滚。

### 6.10 视觉与交互基调

视觉规范见设计系统「墨格」，要点如下。

- **原生 macOS 质感**：整窗工具栏、系统字体、深浅色成对定义并跟随系统。非 Mac 环境回落到 Inter 与 Noto Sans SC。
- **密而不乱**：
  - 正文 13px，行高 30px（紧凑）或 36px（标准）。
  - 间距以 4px 为单位递增。
  - 用灰阶层次和细分隔线分组，不堆卡片阴影。
- **一个强调色**：黛蓝（浅色模式 `#3552D4`，深色模式 `#7D93FF`），只用在可操作的元素和当前选中的状态上。
- **六种状态语义**：已同步、漂移、可更新、脚本变更、来源未知、被覆盖。状态一律用「圆点加短标签」表达，不只靠颜色。漂移用橙色，可更新用蓝色，避开红绿对立。
- **签名元素「层级刻度」**：四个 6px 小方格，依次对应全局、套装、项目、个人，实心格表示该项所在的层。标志取「方中之方」。
- **文件即真相**：路径、哈希、清单片段一律用等宽字体原样展示。
- **同一套交互模式**：
  - 落盘动作都是预览、确认、可撤销。
  - 面板都可以用 × 关闭。
  - 侧栏与列表都可以折叠。
  - 说明性文字能省则省，必要时折叠起来，不长期占用空间。
- **空状态即引导**：没有资产时直接展示体检入口，而不是空白表格。

## 7. 技术架构

### 7.1 选型建议

**Rust 内核 + Tauri 2 外壳 + React 界面。**

- 内核是独立的 Rust 库，桌面应用与命令行共用。这保证 CI 与界面的行为完全一致。
- Tauri 包体小，访问文件系统与钥匙串方便，将来上 Windows 与 Linux 不必重写界面。
- 备选是 SwiftUI 界面加 Rust 内核，Mac 质感最好，但跨平台时界面要重做。你明确提到未来全平台，所以不推荐。

### 7.2 模块

```
┌──────────────── 桌面应用 (Tauri + React) ────────────────┐
│   项目 · 资产库 · 套装 · 全局 · 活动 · 体检 · 菜单栏 · ⌘K  │
└───────────────────────────┬──────────────────────────────┘
                            │              ┌── 命令行 fangcun
┌───────────────────────────▼──────────────▼───────────────┐
│                        内核 (Rust)                        │
│  扫描器 │ 资产库 │ 解析器 │ 物化器 │ 监听器 │ 估算器       │
│  ─────────────────────────────────────────────────────── │
│  适配器层：每个 Agent 工具一份声明式描述                    │
└──────────────────────────────────────────────────────────┘
        │                │                    │
   ~/.fangcun/      项目目录              macOS 钥匙串
   (正本与索引)   (清单、锁、物化产物)
```

- **扫描器**：遍历并归并，产出资产清点与体检发现。同时只读本机各工具的会话记录，统计每项资产近 30 天在哪些项目被触发。这些数据不上传。
- **资产库**：内容寻址存储，git 来源走本地裸仓库缓存，索引用 SQLite。
- **解析器**：合并四层作用域，解出确定结果，写锁。
- **物化器**：计划、应用、快照、回滚。记录所有权。共享的 JSON 与 TOML 按键合并。每次写入记一条到 `~/.fangcun/journal`，活动页读的就是它。
- **监听器**：基于 FSEvents 监听已登记项目与全局目录，发现漂移。
- **估算器**：本地估算 token，明确标注为估算。

### 7.3 适配器是数据，不是代码

各工具的目录约定每月都在变，这是最大的工程风险。适配器因此设计为声明式描述，可独立于应用版本热更新。每份适配器声明：

- 各作用域下 skill、MCP、指令文件的读取位置
- 会话记录的位置与格式，用来统计触发次数
- 同名时的优先级规则
- MCP 配置的文件格式与字段映射
- 能力标记：是否跟随软链、是否支持项目级 MCP、是否支持按项目停用

工具不支持某项能力时，界面明确告知，不静默失败。每个适配器配一套回归样例，工具升级后自动验证。具体路径需在实现时对照各工具当期文档逐一核实，本文不写死。

### 7.4 清单示例

```toml
# fangcun.toml —— 提交到 git
[project]
targets = ["claude-code", "codex"]
mode    = "link"                 # link 或 vendor
budget  = 20000                  # 常驻预算（估算值），不写时 20000

bundles = ["工程基线"]

[skills]
tdd             = { source = "github:obra/superpowers", track = "main" }
skill-b         = { source = "github:acme/skills", pin = "v2.1.0" }
project-harness = { source = "local:luyao-skills", pin = "4d9b1eb" }

[mcp.github]
command = "npx"
args    = ["-y", "@modelcontextprotocol/server-github"]
env     = { GITHUB_TOKEN = "secret:github-token" }   # 值在钥匙串

[instructions]
canonical = "AGENTS.md"          # 正本
mirror    = ["CLAUDE.md"]        # 生成为对正本的引用
```

### 7.5 安全

- 锁里的内容哈希在每次同步时校验，来源被篡改会被拦下。
- 升级差异里，脚本、hook、MCP 启动命令的变化单独高亮。
- 写入范围限定在已登记项目与已知工具配置目录。每次写入前快照。
- 因为需要较宽的文件访问，不走 Mac App Store 沙盒。采用公证过的安装包与 Homebrew 分发。
- 默认零遥测。

## 8. 路线图

按顺序推进，不承诺日期。

| 阶段 | 主题 | 内容 |
|---|---|---|
| **M0** | 透视版，只读 | 扫描、体检报告、生效上下文视图、全局页的只读部分。读取本机会话记录里的触发次数。除方寸自己的 `~/.fangcun` 外不写任何文件。零风险，先建立信任，也最快验证需求 |
| **M1** | MVP 闭环 | 收编、资产库、清单与锁、物化同步、漂移处理、更新回滚、基础密钥、简版套装、命令行。Claude Code 与 Codex |
| **V1.x** | 铺开 | 更多工具适配器。指令片段复用。斜杠命令、子代理、hook、插件纳入管理。CLI 依赖就绪检查。提供方寸自己的 MCP 服务，让 Agent 能直接操作方寸 |
| **V2** | 团队 | 私有团队资产库、组织基线、准入白名单、更新审批、云端与 CI Agent 的引导脚本、远端 CI 的校验记录。Windows 与 Linux |
| **V3** | 质量 | Skill 效果对比试验。会话状态类资产的管理，例如记忆与进度 |

**衡量成功的四个指标**

- 首次价值时间：安装到看见体检报告的时长。
- 重复副本数：收编后应趋近于零。
- 来源已知率：有明确来源与版本的资产占比。
- 常驻上下文降幅：全局瘦身前后各项目的常驻估算值。

## 9. 风险与已定的事

### 9.1 风险

| 风险 | 应对 |
|---|---|
| 工具频繁改目录与格式 | 适配器数据化、可热更新、带回归样例 |
| 厂商原生机制逐步覆盖需求 | 坚持跨工具中立与项目级闭环，原生机制能用就用，不重复造 |
| 赛道拥挤 | 用只读的 M0 快速验证「生效视图」是否真是差异点 |
| 写错用户配置造成损失 | 预览、快照、所有权记录、按键合并。M0 完全只读 |
| 软链在个别工具或 Windows 上不可靠 | 适配器能力标记，自动退回「复制加哈希跟踪」 |
| Token 估算不准 | 始终标注为估算，重在相对比较而非绝对数值 |

### 9.2 已拍板的六件事

2026-11-14 逐条确认。方案正文都按这些结论写成。

| 事项 | 结论 |
|---|---|
| 技术栈 | Rust 内核 + Tauri 2 外壳 + React 界面 |
| 首批工具 | Claude Code 与 Codex 完整支持。其余工具在 M0 只读扫描 |
| 默认物化方式 | 个人项目默认链接。检测到多人协作的仓库时建议入库，登记项目时询问一次 |
| 是否开源 | 全部开源，包括桌面界面。许可证还没有选 |
| 清单格式 | 自有的 `fangcun.toml`，同时支持导入导出 `skills-lock.json` |
| 产品名 | 方寸 Fangcun。命令行叫 `fangcun` |

关于开源：这个产品要写配置、碰密钥，开源是最便宜的信任来源，适配器也适合社区共建。

### 9.3 界面遗留项的结论

第 6 节对照原型后留下八件原型没有覆盖的事，2026-11-14 逐条确认。正文已按结论改写。

| 事项 | 结论 |
|---|---|
| 更新中心放在哪 | 不单独做页面。入口是活动页的待处理项，处理在项目页检查器里，跨项目的批量升级在检查器里勾选受影响的项目 |
| 回滚较早的记录 | 后来的变更也动过同一批文件时，回滚预览里标出来，并要求先回滚后面的记录。不做自动合并 |
| CI 记录怎么回到本机 | 首版只记录本机运行的 `fangcun sync --frozen`，类型改称「校验」。远端 CI 的记录留到 V2 |
| 快照保留多久 | 默认 30 天，并且每个项目至少保留最近 20 个，可在设置里调整。过期后记录仍在，回滚按钮置灰 |
| 密钥操作进不进活动页 | 记录存入、替换、删除三种操作。只记名称和位置，不记值，不提供回滚 |
| 全局层要不要自己的清单 | 首版不做，按原型来 |
| 使用数据从哪一期开始读 | 提前到 M0。只读本机会话记录里的触发次数，不上传 |
| 只有一个项目用到时 | 在转成套装的变更计划里，只勾选一个项目时多给一个选项：不建套装，直接写进那个项目的清单 |

这些结论里有七处当时原型还没有跟上。2026-11-14 已在新画布里补上（链接见 `AGENTS.md`「原型怎么读」），补的地方：

1. 项目页回流完成的提示、活动页升级记录的说明，两处「更新中心」改成「活动」。
2. 项目页检查器的「可更新」区，加上受影响项目的勾选。
3. 活动页的类型和筛选芯片「CI」改成「校验」，触发方去掉 CI。
4. 活动页加「密钥」类型和筛选芯片。
5. 活动页的回滚预览，标出被后来变更动过的文件。
6. 活动页检查器，快照过期后回滚按钮置灰。
7. 全局页的转成套装弹窗，只勾选一个项目时多一个选项。

另外，设计系统封面写的「依据方案第 6.6 节的视觉基调」已改成 6.10。

**M0 实现中定下的六件**，2026-11-14 人逐条确认，都按推荐项。正文已按结论改写。

| 事项 | 结论 |
|---|---|
| M0 能不能写 `~/.fangcun`（D-15） | 能。只写方寸自己的 `~/.fangcun`，用户的任何配置都不写。体检记录存进 `~/.fangcun/journal` |
| M0 的项目从哪来（D-18） | 近 30 天会话记录里出现过的工作目录，归到 git 根目录。侧栏写「近 30 天的项目」，M1 起登记的项目并进来（6.1） |
| 同名时谁生效（D-19） | 生效视图按工具真实规则显示。工具规则相反时物化不自动移动上层的同名项，标「同名冲突」，由人选转成套装或从全局移除（4.3、6.3、6.6） |
| MCP 的常驻（D-20） | M0 标「未估算」。M1 加显式的「试启动并测量」，结果缓存（F5） |
| 全局指令的状态（D-21） | 新状态「全文加载」，灰，不显示用到的项目数（6.6） |
| 项目预算（D-22） | `fangcun.toml` 的 `[project]` 写 `budget`，不写时 20k，全局页用同一个默认值（7.4） |

其中 6.3、6.6 有三处原型当时没跟上，2026-11-14 已在画布里补上：项目页 frontend-design 一行改为项目层被全局层覆盖；全局页 frontend-design 改为「同名冲突 2 处」、不划线；全局页 CLAUDE.md 改为「全文加载」、用到它一栏写「—」。

**原型全量对照后定的两件**，2026-11-14 人选了推荐项。

| 事项 | 结论 |
|---|---|
| 侧栏的项目分组（D-28） | M0 只有「近 30 天的项目」一组。M1 起分两组：「已登记项目」在上，「近 30 天的项目」在下，只列还没登记的目录（6.1） |
| 活动页线框图里的同名记录（D-27） | 按 4.3 改成「与 2 个项目同名冲突」（6.7） |

### 9.4 建议的下一步

先做 M0。它只读、周期短、对你自己立刻有用，并且能用真实数据检验本方案最核心的假设：**「看见生效上下文」是否足以让人愿意把管理权交给一个新工具。**
