# 方寸 Fangcun：Agent 环境管理器 · 产品设计方案

> 初稿 v0.1 · 2026-11-13
> 产品名「方寸」暂取自项目目录名，寓意「方寸之间，上下文井然」。可改。

---

## 1. 结论先行

**一句话定位**：方寸是 Agent 上下文的「包管理器 + 环境管理器」，配一个好用的 Mac 桌面界面。它之于 Skills、MCP、指令文件，相当于 uv 或 mise 之于 Python 依赖与运行时。

**三个核心主张**

1. **Agent 读取的目录是构建产物，不是源。** `.claude/skills`、`.mcp.json`、`CLAUDE.md` 这些位置今天被人手工编辑、到处复制。方寸把它们降级为「由唯一来源生成的输出」。
2. **以项目为中心，而不是以资产库为中心。** 每个项目声明自己需要什么、锁定到哪个版本。全局层尽量薄。
3. **先看见，再管理。** 任何时刻都能回答「这个项目里的 Agent 此刻到底加载了什么、花了多少上下文、谁覆盖了谁」。

**MVP 是一个闭环**：看见 → 收编 → 声明 → 同步 → 更新。覆盖 Skills、MCP、指令文件三类资产，首批完整支持 Claude Code 与 Codex。

**关于命名**：业界说 harness 多指 Agent 运行时本身，例如 Claude Code、Codex。你描述的是运行时之上「可配置、可移植的那一层」。本文把它叫做 **Agent 环境**（项目级的整体）和 **上下文资产**（其中的每一件）。「project harness」作为口语别名保留。

## 2. 痛点深挖

### 2.1 你的机器就是证据

写方案前我只读扫描了本机，结果如下。

| 观察 | 事实 |
|---|---|
| Agent 工具数量 | 主目录下有 7 个工具的配置目录：Claude Code、Codex、Cursor、Gemini、opencode、Copilot、Windsurf。项目里还出现了 Trae。 |
| 同一 skill 的副本 | `project-harness` 在 5 个项目里各有一份。4 份内容相同，`evals_studio/.trae` 里那份已经分叉。 |
| 没有唯一来源 | `luyao-skills`、`my-skills`、`agent-skill`、`harness` 四个仓库里存放着内容相同的 skill。哪个是正本无从判断。 |
| 各工具分发不一致 | `~/.agents/skills` 有 31 个 skill。Claude Code 只链接了其中 16 个，Windsurf 有 20 个，Codex 有 3 个。 |
| 全局污染 | 本次会话开在一个空目录里，16 个飞书 skill 的描述仍全部进入了上下文。 |
| 版本停滞 | 全局锁文件最后修改于 7 月 5 日，而 skills 目录 11 月 11 日还在变动。锁与实际已脱节。 |
| MCP 配置分散 | 至少四处各自为政：`~/.claude.json`、`~/.codex/config.toml`、`~/.gemini/settings.json`、opencode 配置。 |

### 2.2 你提出的痛点

| 痛点 | 本质 |
|---|---|
| 不同项目要求不同的资产与版本 | 缺少项目级的需求声明与版本锁定 |
| 用户级与项目级冲突、无效占据上下文 | 作用域只有「全局 / 项目」两档，且生效结果不可见 |
| 版本经常得不到更新 | 资产没有来源记录，更新没有入口也没有提醒 |
| 一份 skill 复制得到处都是 | 没有唯一来源，复制是唯一的分发手段 |

### 2.3 你还没提到、但同样要命的痛点

1. **生效上下文不可见。** 托管层、用户层、项目层、本地层、插件层、子目录指令层层叠加，每个工具的优先级规则还不一样。没有人能一眼说出「最终生效的是什么」。
2. **上下文预算税。** 每个 skill 的名称与描述常驻上下文，每个 MCP 服务的工具定义也要占位，指令文件全文加载。全局装一个，所有项目都缴税。
3. **多工具碎片化。** 指令文件有 `CLAUDE.md`、`AGENTS.md`、`GEMINI.md`。MCP 配置有 JSON 也有 TOML。同一份意图要维护 N 种格式。
4. **原地修改无法回流。** Agent 工作时经常顺手改进项目里的 skill 副本。这些改进留在副本里，永远回不到来源，也到不了其他项目。
5. **供应链与信任。** Skill 带脚本，hook 执行任意命令，MCP 服务拿着你的凭据运行。上游一次静默更新就能改变 Agent 行为。
6. **密钥裸奔。** MCP 配置里的 API Key 以明文存在，随复制扩散，偶尔还被提交进 git。
7. **不可复现。** 新同事、新电脑、git worktree、云端或 CI 里的 Agent，都拿不到和你一样的环境。「在我的 Agent 上是好的」。
8. **隐式依赖。** Skill 依赖某个 CLI、某个 MCP 服务、某个环境变量，却从不声明。缺了就静默失效。
9. **个人与团队混在一起。** 哪些该提交给团队、哪些只是个人偏好，现有机制没有清晰的分层。
10. **只进不出。** 没有使用数据，不知道哪些 skill 从未被触发。资产只增不减，越积越乱。
11. **无法回滚与试验。** 改了一个 skill 效果变差，没有后悔药，也没法对比。
12. **作用域太粗。** 真实需求是「我所有前端项目」「这个客户的项目」「工作与个人」。全局与项目两档表达不了。

### 2.4 五个根因

所有痛点可以归到五个根因，产品的五个支柱一一对应。

| 根因 | 对应支柱 |
|---|---|
| A. 没有唯一来源 | 资产库 |
| B. 项目需求没有声明 | 项目清单与锁 |
| C. 生效结果不可见 | 生效上下文视图 |
| D. 目标格式碎片化 | 适配器与物化 |
| E. 没有生命周期 | 更新、回滚、回流 |

这其实是一个被解决过很多次的问题。Python 从全局 site-packages 走到 virtualenv 加锁文件。Node 从全局安装走到 `package.json`。Agent 上下文今天正处在「全局 site-packages」阶段。

## 3. 现状与竞品

以下判断基于各项目的自述页面，我没有逐一试用。这个领域每月都在变，立项前建议实测前三名。

| 类别 | 代表 | 解决了什么 | 留下的空白 |
|---|---|---|---|
| Skill 命令行 | [vercel-labs/skills](https://github.com/vercel-labs/skills) | 安装、软链到多个工具、全局锁与项目锁 | 只管 skill。锁里只有哈希没有版本语义。没有可见性。[删除后锁残留](https://github.com/renovatebot/renovate/discussions/41841)等粗糙处仍在 |
| Skill 桌面库 | [skills-manage](https://github.com/zhaikong/skills-manage)、[Skills Manager](https://skillsmanager.dev/)、[Skill Desktop](https://skill-desktop-labs.github.io/skill-desktop-landing/)、[Agent Desk](https://agentdesk.sh/) | 一个库分发到几十个工具 | 以库为中心，本质是「全局分发器」。项目级版本锁定与生效视图薄弱 |
| MCP 管理器 | [MCP Linker](https://mcp-linker.milisp.dev/)、[Claude Code Tool Manager](https://github.com/tylergraydev/claude-code-tool-manager)、[mTarsier](https://mtarsier.com/) | 多客户端 MCP 配置同步，部分支持按项目指派 | 与 skill、指令割裂。密钥与复现不是重点 |
| 锁与体检命令行 | [skillock](https://github.com/quantz8a/skillock)、[agent-skills-cli](https://github.com/Karanjot786/agent-skills-cli) | 锁文件、token 预算、冲突检测 | 只有命令行，各管一段，没有闭环 |
| 原生机制 | Claude Code 插件与市场 | 打包分发、按项目启用 | 只在单一工具内有效 |

**空白在哪里**：现有产品几乎都在回答「怎么把一个库同步到 N 个工具」。没有产品把这四件事合在一起：

- 以项目为中心的声明与逐项目版本锁定
- 跨资产类型统一管理：skill、MCP、指令
- 生效上下文的透视与预算
- 副本修改的回流

**必须正视的事实**：赛道已经拥挤。方寸的差异不能靠功能清单，要靠「项目中心的闭环」和体验质量。[agentskills.io 的实现指南](https://agentskills.io/client-implementation/adding-skills-support)已约定项目级覆盖用户级并建议提示用户，说明「遮蔽可见性」是公认需求但尚无好的界面。

## 4. 核心理念与概念模型

### 4.1 一条流水线

```
来源 Source ──▶ 资产库 Library ──▶ 清单 + 锁 ──▶ 物化 Sync ──▶ 生效视图 X-Ray
(git/本地/市场)   (唯一正本，带版本)   (项目声明)     (写入各工具原生位置)   (看见结果)
                        ▲                                  │
                        └────────── 回流 Promote ◀──────────┘
                                 (副本被改，决定去留)
```

### 4.2 七个概念

| 概念 | 含义 | 类比 |
|---|---|---|
| **资产 Asset** | 一件可被 Agent 读取的东西。MVP 含三类：Skill、MCP 服务、指令文件 | 包 |
| **来源 Source** | 资产的出处：git 仓库、本地开发目录、公开市场 | 注册表 |
| **资产库 Library** | 本机唯一正本，按内容寻址存储，保留每个版本 | 包缓存 |
| **套装 Bundle** | 一组资产的命名集合，例如「飞书办公」「前端基线」 | 依赖组 |
| **清单 Manifest** | 项目根目录的 `fangcun.toml`，声明目标工具、资产、版本约束 | `package.json` |
| **锁 Lock** | `fangcun.lock`，记录解析出的确切提交与内容哈希 | 锁文件 |
| **物化 Sync** | 把解析结果写进各工具的原生位置，并记录哪些文件归方寸管 | 安装 |

### 4.3 作用域：从两档变四层

```
全局基线   尽量薄，只放真正每个项目都要的
   ▼
套装       按项目类型、客户、场景复用
   ▼
项目清单   提交到 git，团队共享
   ▼
个人覆盖   fangcun.local.toml，不提交，只属于你
```

下层覆盖上层。覆盖关系在界面里永远可见，不靠记忆。

### 4.4 版本是什么

Skill 规范本身没有版本字段。方寸定义版本为「来源提交 + 内容哈希」。有 git 标签就显示标签，没有就显示日期与短哈希。每项资产有两种跟随方式：

- **固定 Pin**：锁死在某个版本，只有手动才变。
- **跟随 Track**：跟着某个分支，有新版本时提醒，确认后才更新。

### 4.5 你的例子怎么解

项目 A 要 Skill A v1、Skill B v1。项目 B 要 Skill B v2、Skill C v1。

- 资产库里 Skill B 的 v1 与 v2 并存，各一份。
- 项目 A 的清单固定 B 到 v1，项目 B 固定到 v2。各自物化进自己的项目目录。
- 全局层不安装 B，于是不存在覆盖干扰。
- 上游出 v3 时，更新中心同时列出两个项目，各自决定是否升级。

### 4.6 六条设计原则

1. **不发明运行时。** 只写各工具的原生位置。卸载方寸后一切照常工作。
2. **文件即真相。** 清单与锁是纯文本，可读、可提交、可审查。界面只是它们的编辑器。
3. **预览先于写入。** 任何落盘动作先出变更计划，确认后才执行。
4. **一切可撤销。** 每次同步都是一个快照，可一键回退。
5. **只动自己的东西。** 记录所有权。共享文件按键合并，绝不整文件覆盖。
6. **本地优先。** 不需要账号，默认不上传任何数据。

## 5. MVP 核心功能

MVP 的范围是六项能力。每项都直接对应第 2 节的痛点。

### F1 全盘体检与收编

- 扫描主目录与你登记的项目目录，识别所有工具的 skill、MCP、指令文件。
- 按内容哈希归并：哪些是同一份的副本、哪些已经分叉、哪些来源未知。
- 输出体检报告，每条发现配一个可撤销的一键动作。
- 「收编」把选中的资产移入资产库，原位置替换为受管链接，事前自动备份。

**验收**：从安装到看到体检报告不超过两分钟，全程零配置。在你的机器上应能直接报出「project-harness 有 5 份副本，其中 1 份已分叉」。

### F2 资产库

- 按内容寻址存储，多版本并存。
- 三种来源：git 仓库、本地开发目录、公开 skill 市场。
- 本地开发目录是「活链接」：你在自己的 skill 仓库里改，登记为开发模式的项目立即可见。
- 每项资产显示：来源、版本历史、被哪些项目使用、预估 token 成本、是否含脚本。

**验收**：同一 skill 在本机只有一份正本。任一资产都能回答「从哪来、谁在用、哪个版本」。

### F3 项目环境：清单与锁

- 登记项目后生成 `fangcun.toml` 与 `fangcun.lock`。
- 声明目标工具、套装、资产与版本约束、物化方式。
- `fangcun.local.toml` 承载个人覆盖，自动加入 `.gitignore`。
- 能从现状反推：对已有项目，直接把当前目录里的资产反向生成清单。
- 能导入 `skills-lock.json`，与现有命令行生态互通。

**验收**：新机器上克隆仓库，一条命令或一次点击即可还原完全相同的环境。

### F4 物化同步与漂移处理

- 先出变更计划，列出将新增、修改、删除的每个文件。
- 两种物化方式，按项目选择：
  - **链接**：项目目录里是指向资产库的软链，零重复，适合个人项目。
  - **入库**：实体文件提交进仓库，同事与云端 Agent 无需安装方寸，适合团队项目。
- 多工具去重：实体只放一份在 `.agents/skills`，其他工具目录用相对软链指过去。
- 文件监听发现受管副本被修改时，给三个选择：**回流**到来源、**丢弃**修改、**分叉**为项目专属。

**验收**：同步不触碰任何非受管文件。Agent 在项目里改了 skill，五秒内出现漂移提示。

### F5 生效上下文视图

这是方寸的招牌界面，也是与竞品最大的区别。

- 按「项目 × 工具」展示 Agent 实际加载的全部内容，标明每一项来自哪一层。
- 标出被覆盖、重名冲突、重复加载、来源未知。
- 上下文预算条：常驻成本与按需成本分开估算，并标明是估算值。
- 就地操作：从全局降级为按项目、在本项目停用、查看覆盖它的是谁。
- 插件、hook、子代理、斜杠命令在 MVP 里只读展示，不管理。

**验收**：对任一项目，十秒内回答「加载了什么、谁覆盖了谁、常驻占多少」。

### F6 更新、回滚与密钥

- 更新中心：列出有新版本的资产与受影响项目，展示差异，脚本与命令变更高亮警示。
- 可逐项目升级，也可批量升级。每次同步留快照，一键回滚。
- MCP 密钥存入 macOS 钥匙串。提交进仓库的配置只含环境变量引用，明文只落在不提交的本地配置里。
- 体检会报告「已提交文件里有明文密钥」。

**验收**：升级前必能看到差异。回滚后磁盘状态与上一快照逐字节一致。

### 配套：命令行

桌面应用与命令行共用同一个内核。命令行让 CI、云端 Agent、worktree 无需界面也能还原环境。

```bash
fangcun status        # 当前项目的同步状态与漂移
fangcun sync          # 按清单与锁物化
fangcun sync --frozen # CI 用：锁与清单不一致就失败
fangcun add <资产>     # 加入清单
fangcun update        # 检查并升级
fangcun why <资产>     # 解释它为何生效、来自哪一层
```

### MVP 明确不做

- 不管理会话状态类资产，例如记忆、任务进度文档。它们是「演化中的状态」而非「配置」，机制不同。
- 不做自建市场，不做账号体系，不做云同步。
- 不代理或拦截 Agent 运行，不做 MCP 网关。
- 不安装 CLI 依赖。只在后续版本做「依赖是否就绪」的检查。
- 不做 skill 质量评测。

## 6. 关键界面与体验流程

### 6.1 形态

- **主窗口**：三栏布局。侧栏导航，中间列表，右侧检查器。
- **菜单栏常驻图标**：显示漂移与可更新的角标，可快速跳到项目。
- **命令面板** `⌘K`：搜索资产、项目、动作。键盘优先。
- **命令行** `fangcun`：见上节。

侧栏只有五项：**项目**、**资产库**、**套装**、**全局**、**活动**。

本节线框图均为示意。其中的数字与状态用来说明界面形态，不全是实测结果。

### 6.5 四条关键流程

1. **给项目加资产**：`⌘K` 搜索，回车加入，弹出变更计划，应用。全程不离开键盘。
2. **处理漂移**：点漂移标记，看差异，三选一。选「回流」时列出同样使用该资产的其他项目，逐个决定是否跟进。
3. **升级**：更新中心看差异，脚本改动标红，选项目，应用。不满意就在「活动」里回滚。
4. **全局瘦身**：「全局」页按「给每个项目带来的常驻成本」排序。选中一批，一步转成套装，再勾选哪些项目需要它。

### 6.6 视觉与交互基调

- 原生 macOS 质感：侧栏毛玻璃、系统字体、系统图标、深浅色自动跟随。
- 信息密度参考 Linear 与 Raycast：密而不乱，状态用颜色点与短标签表达。
- 所有破坏性动作走「预览、确认、可撤销」同一套模式，用户只需学一次。
- 空状态即引导。没有资产时直接展示体检入口，而不是空白表格。

## 7. 技术架构

### 7.1 选型建议

**Rust 内核 + Tauri 2 外壳 + React 界面。**

- 内核是独立的 Rust 库，桌面应用与命令行共用。这保证 CI 与界面的行为完全一致。
- Tauri 包体小，访问文件系统与钥匙串方便，将来上 Windows 与 Linux 不必重写界面。
- 备选是 SwiftUI 界面加 Rust 内核，Mac 质感最好，但跨平台时界面要重做。你明确提到未来全平台，所以不推荐。

### 7.2 模块

```
┌──────────────── 桌面应用 (Tauri + React) ────────────────┐
│   项目页 · 资产库 · 体检 · 更新中心 · 菜单栏 · ⌘K          │
└───────────────────────────┬──────────────────────────────┘
                            │              ┌── 命令行 fangcun
┌───────────────────────────▼──────────────▼───────────────┐
│                        内核 (Rust)                        │
│  扫描器 │ 资产库 │ 解析器 │ 物化器 │ 监听器 │ 估算器       │
│  ─────────────────────────────────────────────────────── │
│  适配器层：每个 Agent 工具一份声明式描述                    │
└──────────────────────────────────────────────────────────┘
        │                │                    │
   ~/.fangcun/      项目目录              macOS 钥匙串
   (正本与索引)   (清单、锁、物化产物)
```

- **扫描器**：遍历并归并，产出资产清点与体检发现。
- **资产库**：内容寻址存储，git 来源走本地裸仓库缓存，索引用 SQLite。
- **解析器**：合并四层作用域，解出确定结果，写锁。
- **物化器**：计划、应用、快照、回滚。记录所有权。共享的 JSON 与 TOML 按键合并。
- **监听器**：基于 FSEvents 监听已登记项目与全局目录，发现漂移。
- **估算器**：本地估算 token，明确标注为估算。

### 7.3 适配器是数据，不是代码

各工具的目录约定每月都在变，这是最大的工程风险。适配器因此设计为声明式描述，可独立于应用版本热更新。每份适配器声明：

- 各作用域下 skill、MCP、指令文件的读取位置
- 同名时的优先级规则
- MCP 配置的文件格式与字段映射
- 能力标记：是否跟随软链、是否支持项目级 MCP、是否支持按项目停用

工具不支持某项能力时，界面明确告知，不静默失败。每个适配器配一套回归样例，工具升级后自动验证。具体路径需在实现时对照各工具当期文档逐一核实，本文不写死。

### 7.4 清单示例

```toml
# fangcun.toml —— 提交到 git
[project]
targets = ["claude-code", "codex"]
mode    = "link"                 # link 或 vendor

bundles = ["工程基线"]

[skills]
tdd             = { source = "github:obra/superpowers", track = "main" }
skill-b         = { source = "github:acme/skills", pin = "v2.1.0" }
project-harness = { source = "local:luyao-skills", pin = "4d9b1eb" }

[mcp.github]
command = "npx"
args    = ["-y", "@modelcontextprotocol/server-github"]
env     = { GITHUB_TOKEN = "secret:github-token" }   # 值在钥匙串

[instructions]
canonical = "AGENTS.md"          # 正本
mirror    = ["CLAUDE.md"]        # 生成为对正本的引用
```

### 7.5 安全

- 锁里的内容哈希在每次同步时校验，来源被篡改会被拦下。
- 升级差异里，脚本、hook、MCP 启动命令的变化单独高亮。
- 写入范围限定在已登记项目与已知工具配置目录。每次写入前快照。
- 因为需要较宽的文件访问，不走 Mac App Store 沙盒。采用公证过的安装包与 Homebrew 分发。
- 默认零遥测。

## 8. 路线图

按顺序推进，不承诺日期。

| 阶段 | 主题 | 内容 |
|---|---|---|
| **M0** | 透视版，只读 | 扫描、体检报告、生效上下文视图。不写任何文件。零风险，先建立信任，也最快验证需求 |
| **M1** | MVP 闭环 | 收编、资产库、清单与锁、物化同步、漂移处理、更新回滚、基础密钥、简版套装、命令行。Claude Code 与 Codex |
| **V1.x** | 铺开 | 更多工具适配器。指令片段复用。斜杠命令、子代理、hook、插件纳入管理。CLI 依赖就绪检查。基于本地会话记录的使用洞察，提示从未触发的资产。提供方寸自己的 MCP 服务，让 Agent 能直接操作方寸 |
| **V2** | 团队 | 私有团队资产库、组织基线、准入白名单、更新审批、云端与 CI Agent 的引导脚本。Windows 与 Linux |
| **V3** | 质量 | Skill 效果对比试验。会话状态类资产的管理，例如记忆与进度 |

**衡量成功的四个指标**

- 首次价值时间：安装到看见体检报告的时长。
- 重复副本数：收编后应趋近于零。
- 来源已知率：有明确来源与版本的资产占比。
- 常驻上下文降幅：全局瘦身前后各项目的常驻估算值。

## 9. 风险与待你决策的问题

### 9.1 风险

| 风险 | 应对 |
|---|---|
| 工具频繁改目录与格式 | 适配器数据化、可热更新、带回归样例 |
| 厂商原生机制逐步覆盖需求 | 坚持跨工具中立与项目级闭环，原生机制能用就用，不重复造 |
| 赛道拥挤 | 用只读的 M0 快速验证「生效视图」是否真是差异点 |
| 写错用户配置造成损失 | 预览、快照、所有权记录、按键合并。M0 完全只读 |
| 软链在个别工具或 Windows 上不可靠 | 适配器能力标记，自动退回「复制加哈希跟踪」 |
| Token 估算不准 | 始终标注为估算，重在相对比较而非绝对数值 |

### 9.2 需要你拍板的六件事

我给出了推荐项。方案正文都按推荐项写成。

1. **技术栈**。推荐 Rust 内核加 Tauri 2。若你更看重极致的 Mac 原生质感且接受跨平台重做界面，可改 SwiftUI。
2. **首批工具**。推荐 Claude Code 与 Codex 完整支持，其余工具在 M0 只读扫描。你日常若主用 Windsurf 或 Trae，应调整顺序。
3. **默认物化方式**。推荐个人项目默认链接，检测到多人协作的仓库时建议入库，登记项目时询问一次。
4. **是否开源**。推荐内核与命令行开源。这个产品要写配置、碰密钥，开源是最便宜的信任来源，适配器也适合社区共建。团队功能留作商业化空间。
5. **清单格式**。推荐自有的 `fangcun.toml`，同时支持导入导出 `skills-lock.json`。不建议一开始就绑定某个现有格式，它们只覆盖 skill 一类。
6. **产品名**。「方寸」是我从目录名推断的，请确认。

### 9.3 建议的下一步

先做 M0。它只读、周期短、对你自己立刻有用，并且能用真实数据检验本方案最核心的假设：**「看见生效上下文」是否足以让人愿意把管理权交给一个新工具。**
