> v0.3 · 2026-11-14 · 第 6 节已与高保真原型（fangcun-ds v0.1，2026-11-13）同步；全局页与活动页为新增设计，画板待补

## 1. 结论先行

**一句话定位**：方寸是 Agent 上下文的「包管理器 + 环境管理器」，配一个好用的 Mac 桌面界面。它之于 Skills、MCP、指令文件，相当于 uv 或 mise 之于 Python 依赖与运行时。

**三个核心主张**

1. **Agent 读取的目录是构建产物，不是源。** `.claude/skills`、`.mcp.json`、`CLAUDE.md` 这些位置今天被人手工编辑、到处复制。方寸把它们降级为「由唯一来源生成的输出」。
2. **以项目为中心，而不是以资产库为中心。** 每个项目声明自己需要什么、锁定到哪个版本。全局层尽量薄。
3. **先看见，再管理。** 任何时刻都能回答「这个项目里的 Agent 此刻到底加载了什么、花了多少上下文、谁覆盖了谁」。

**MVP 是一个闭环**：看见 → 收编 → 声明 → 同步 → 更新。覆盖 Skills、MCP、指令文件三类资产，首批完整支持 Claude Code 与 Codex。

**关于命名**：业界说 harness 多指 Agent 运行时本身，例如 Claude Code、Codex。你描述的是运行时之上「可配置、可移植的那一层」。本文把它叫做 **Agent 环境**（项目级的整体）和 **上下文资产**（其中的每一件）。「project harness」作为口语别名保留。

## 2. 痛点深挖

### 2.1 你的机器就是证据

写方案前我只读扫描了本机，结果如下。

| 观察 | 事实 |
|---|---|
| Agent 工具数量 | 主目录下有 7 个工具的配置目录：Claude Code、Codex、Cursor、Gemini、opencode、Copilot、Windsurf。项目里还出现了 Trae。 |
| 同一 skill 的副本 | `project-harness` 在 5 个项目里各有一份。4 份内容相同，`evals_studio/.trae` 里那份已经分叉。 |
| 没有唯一来源 | `luyao-skills`、`my-skills`、`agent-skill`、`harness` 四个仓库里存放着内容相同的 skill。哪个是正本无从判断。 |
| 各工具分发不一致 | `~/.agents/skills` 有 31 个 skill。Claude Code 只链接了其中 16 个，Windsurf 有 20 个，Codex 有 3 个。 |
| 全局污染 | 本次会话开在一个空目录里，16 个飞书 skill 的描述仍全部进入了上下文。 |
| 版本停滞 | 全局锁文件最后修改于 7 月 5 日，而 skills 目录 11 月 11 日还在变动。锁与实际已脱节。 |
| MCP 配置分散 | 至少四处各自为政：`~/.claude.json`、`~/.codex/config.toml`、`~/.gemini/settings.json`、opencode 配置。 |

### 2.2 你提出的痛点

| 痛点 | 本质 |
|---|---|
| 不同项目要求不同的资产与版本 | 缺少项目级的需求声明与版本锁定 |
| 用户级与项目级冲突、无效占据上下文 | 作用域只有「全局 / 项目」两档，且生效结果不可见 |
| 版本经常得不到更新 | 资产没有来源记录，更新没有入口也没有提醒 |
| 一份 skill 复制得到处都是 | 没有唯一来源，复制是唯一的分发手段 |

### 2.3 你还没提到、但同样要命的痛点

1. **生效上下文不可见。** 托管层、用户层、项目层、本地层、插件层、子目录指令层层叠加，每个工具的优先级规则还不一样。没有人能一眼说出「最终生效的是什么」。
2. **上下文预算税。** 每个 skill 的名称与描述常驻上下文，每个 MCP 服务的工具定义也要占位，指令文件全文加载。全局装一个，所有项目都缴税。
3. **多工具碎片化。** 指令文件有 `CLAUDE.md`、`AGENTS.md`、`GEMINI.md`。MCP 配置有 JSON 也有 TOML。同一份意图要维护 N 种格式。
4. **原地修改无法回流。** Agent 工作时经常顺手改进项目里的 skill 副本。这些改进留在副本里，永远回不到来源，也到不了其他项目。
5. **供应链与信任。** Skill 带脚本，hook 执行任意命令，MCP 服务拿着你的凭据运行。上游一次静默更新就能改变 Agent 行为。
6. **密钥裸奔。** MCP 配置里的 API Key 以明文存在，随复制扩散，偶尔还被提交进 git。
7. **不可复现。** 新同事、新电脑、git worktree、云端或 CI 里的 Agent，都拿不到和你一样的环境。「在我的 Agent 上是好的」。
8. **隐式依赖。** Skill 依赖某个 CLI、某个 MCP 服务、某个环境变量，却从不声明。缺了就静默失效。
9. **个人与团队混在一起。** 哪些该提交给团队、哪些只是个人偏好，现有机制没有清晰的分层。
10. **只进不出。** 没有使用数据，不知道哪些 skill 从未被触发。资产只增不减，越积越乱。
11. **无法回滚与试验。** 改了一个 skill 效果变差，没有后悔药，也没法对比。
12. **作用域太粗。** 真实需求是「我所有前端项目」「这个客户的项目」「工作与个人」。全局与项目两档表达不了。

### 2.4 五个根因

所有痛点可以归到五个根因，产品的五个支柱一一对应。

| 根因 | 对应支柱 |
|---|---|
| A. 没有唯一来源 | 资产库 |
| B. 项目需求没有声明 | 项目清单与锁 |
| C. 生效结果不可见 | 生效上下文视图 |
| D. 目标格式碎片化 | 适配器与物化 |
| E. 没有生命周期 | 更新、回滚、回流 |

这其实是一个被解决过很多次的问题。Python 从全局 site-packages 走到 virtualenv 加锁文件。Node 从全局安装走到 `package.json`。Agent 上下文今天正处在「全局 site-packages」阶段。

## 3. 现状与竞品

以下判断基于各项目的自述页面，我没有逐一试用。这个领域每月都在变，立项前建议实测前三名。

| 类别 | 代表 | 解决了什么 | 留下的空白 |
|---|---|---|---|
| Skill 命令行 | [vercel-labs/skills](https://github.com/vercel-labs/skills) | 安装、软链到多个工具、全局锁与项目锁 | 只管 skill。锁里只有哈希没有版本语义。没有可见性。[删除后锁残留](https://github.com/renovatebot/renovate/discussions/41841)等粗糙处仍在 |
| Skill 桌面库 | [skills-manage](https://github.com/zhaikong/skills-manage)、[Skills Manager](https://skillsmanager.dev/)、[Skill Desktop](https://skill-desktop-labs.github.io/skill-desktop-landing/)、[Agent Desk](https://agentdesk.sh/) | 一个库分发到几十个工具 | 以库为中心，本质是「全局分发器」。项目级版本锁定与生效视图薄弱 |
| MCP 管理器 | [MCP Linker](https://mcp-linker.milisp.dev/)、[Claude Code Tool Manager](https://github.com/tylergraydev/claude-code-tool-manager)、[mTarsier](https://mtarsier.com/) | 多客户端 MCP 配置同步，部分支持按项目指派 | 与 skill、指令割裂。密钥与复现不是重点 |
| 锁与体检命令行 | [skillock](https://github.com/quantz8a/skillock)、[agent-skills-cli](https://github.com/Karanjot786/agent-skills-cli) | 锁文件、token 预算、冲突检测 | 只有命令行，各管一段，没有闭环 |
| 原生机制 | Claude Code 插件与市场 | 打包分发、按项目启用 | 只在单一工具内有效 |

**空白在哪里**：现有产品几乎都在回答「怎么把一个库同步到 N 个工具」。没有产品把这四件事合在一起：

- 以项目为中心的声明与逐项目版本锁定
- 跨资产类型统一管理：skill、MCP、指令
- 生效上下文的透视与预算
- 副本修改的回流

**必须正视的事实**：赛道已经拥挤。方寸的差异不能靠功能清单，要靠「项目中心的闭环」和体验质量。[agentskills.io 的实现指南](https://agentskills.io/client-implementation/adding-skills-support)已约定项目级覆盖用户级并建议提示用户，说明「遮蔽可见性」是公认需求但尚无好的界面。

## 4. 核心理念与概念模型

### 4.1 一条流水线

```
来源 Source ──▶ 资产库 Library ──▶ 清单 + 锁 ──▶ 物化 Sync ──▶ 生效视图 X-Ray
(git/本地/市场)   (唯一正本，带版本)   (项目声明)     (写入各工具原生位置)   (看见结果)
                        ▲                                  │
                        └────────── 回流 Promote ◀──────────┘
                                 (副本被改，决定去留)
```

### 4.2 七个概念

| 概念 | 含义 | 类比 |
|---|---|---|
| **资产 Asset** | 一件可被 Agent 读取的东西。MVP 含三类：Skill、MCP 服务、指令文件 | 包 |
| **来源 Source** | 资产的出处：git 仓库、本地开发目录、公开市场 | 注册表 |
| **资产库 Library** | 本机唯一正本，按内容寻址存储，保留每个版本 | 包缓存 |
| **套装 Bundle** | 一组常一起用的资产，起个名字给多个项目复用，例如「飞书办公」「前端基线」 | 依赖组 |
| **清单 Manifest** | 项目根目录的 `fangcun.toml`，声明目标工具、资产、版本约束 | `package.json` |
| **锁 Lock** | `fangcun.lock`，记录解析出的确切提交与内容哈希 | 锁文件 |
| **物化 Sync** | 把解析结果写进各工具的原生位置，并记录哪些文件归方寸管 | 安装 |

### 4.3 作用域：从两档变四层

```
全局基线   尽量薄，只放真正每个项目都要的
   ▼
套装       按项目类型、客户、场景复用
   ▼
项目清单   提交到 git，团队共享
   ▼
个人覆盖   fangcun.local.toml，不提交，只属于你
```

下层覆盖上层。覆盖关系在界面里永远可见，不靠记忆。

### 4.4 版本是什么

Skill 规范本身没有版本字段。方寸定义版本为「来源提交 + 内容哈希」。有 git 标签就显示标签，没有就显示日期与短哈希。每项资产有两种跟随方式：

- **固定 Pin**：锁死在某个版本，只有手动才变。
- **跟随 Track**：跟着某个分支，有新版本时提醒，确认后才更新。

### 4.5 你的例子怎么解

项目 A 要 Skill A v1、Skill B v1。项目 B 要 Skill B v2、Skill C v1。

- 资产库里 Skill B 的 v1 与 v2 并存，各一份。
- 项目 A 的清单固定 B 到 v1，项目 B 固定到 v2。各自物化进自己的项目目录。
- 全局层不安装 B，于是不存在覆盖干扰。
- 上游出 v3 时，更新中心同时列出两个项目，各自决定是否升级。

### 4.6 六条设计原则

1. **不发明运行时。** 只写各工具的原生位置。卸载方寸后一切照常工作。
2. **文件即真相。** 清单与锁是纯文本，可读、可提交、可审查。界面只是它们的编辑器。
3. **预览先于写入。** 任何落盘动作先出变更计划，确认后才执行。
4. **一切可撤销。** 每次同步都是一个快照，可一键回退。
5. **只动自己的东西。** 记录所有权。共享文件按键合并，绝不整文件覆盖。
6. **本地优先。** 不需要账号，默认不上传任何数据。

## 5. MVP 核心功能

MVP 的范围是六项能力。每项都直接对应第 2 节的痛点。

### F1 全盘体检与收编

- 扫描主目录与你登记的项目目录，识别所有工具的 skill、MCP、指令文件。
- 按内容哈希归并：哪些是同一份的副本、哪些已经分叉、哪些来源未知。
- 输出体检报告，每条发现配一个可撤销的一键动作。
- 「收编」把选中的资产移入资产库，原位置替换为受管链接，事前自动备份。

**验收**：从安装到看到体检报告不超过两分钟，全程零配置。在你的机器上应能直接报出「project-harness 有 5 份副本，其中 1 份已分叉」。

### F2 资产库

- 按内容寻址存储，多版本并存。
- 三种来源：git 仓库、本地开发目录、公开 skill 市场。
- 本地开发目录是「活链接」：你在自己的 skill 仓库里改，登记为开发模式的项目立即可见。
- 每项资产显示：来源、版本历史、被哪些项目使用、预估 token 成本、是否含脚本。
- 按类型与来源筛选，来源按本地开发、GitHub、npm、待收编分组。

**验收**：同一 skill 在本机只有一份正本。任一资产都能回答「从哪来、谁在用、哪个版本」。

### F3 项目环境：清单与锁

- 登记项目后生成 `fangcun.toml` 与 `fangcun.lock`。
- 声明目标工具、套装、资产与版本约束、物化方式。
- `fangcun.local.toml` 承载个人覆盖，自动加入 `.gitignore`。
- 能从现状反推：对已有项目，直接把当前目录里的资产反向生成清单。
- 能导入 `skills-lock.json`，与现有命令行生态互通。

**验收**：新机器上克隆仓库，一条命令或一次点击即可还原完全相同的环境。

### F4 物化同步与漂移处理

- 先出变更计划，列出将新增、修改、删除的每个文件。
- 两种物化方式，按项目选择：
  - **链接**：项目目录里是指向资产库的软链，零重复，适合个人项目。
  - **入库**：实体文件提交进仓库，同事与云端 Agent 无需安装方寸，适合团队项目。
- 多工具去重：实体只放一份在 `.agents/skills`，其他工具目录用相对软链指过去。
- 文件监听发现受管副本被修改时，给三个选择：**回流**到来源、**丢弃**修改、**分叉**为项目专属。

**验收**：同步不触碰任何非受管文件。Agent 在项目里改了 skill，五秒内出现漂移提示。

### F5 生效上下文视图

这是方寸的招牌界面，也是与竞品最大的区别。

- 按「项目 × 工具」展示 Agent 实际加载的全部内容，标明每一项来自哪一层。
- 标出被覆盖、重名冲突、重复加载、来源未知。
- 上下文预算条：常驻成本与按需成本分开估算，并标明是估算值。
- 就地操作：从全局降级为按项目、在本项目停用、查看覆盖它的是谁。
- 每一项都能看到：为什么是这个状态、在哪一层声明、占多少常驻、写入了哪些文件、最近活动。
- 插件、hook、子代理、斜杠命令在 MVP 里只看不管：逐行展示，不提供操作，不计入预算。

**验收**：对任一项目，十秒内回答「加载了什么、谁覆盖了谁、常驻占多少」。

### F6 更新、回滚与密钥

- 更新中心：列出有新版本的资产与受影响项目，展示差异，脚本与命令变更高亮警示。
- 可逐项目升级，也可批量升级。每次同步留快照，一键回滚。
- MCP 密钥存入 macOS 钥匙串。提交进仓库的配置只含环境变量引用，明文只落在不提交的本地配置里。
- 体检会报告「已提交文件里有明文密钥」。

**验收**：升级前必能看到差异。回滚后磁盘状态与上一快照逐字节一致。

### 配套：命令行

桌面应用与命令行共用同一个内核。命令行让 CI、云端 Agent、worktree 无需界面也能还原环境。

```bash
fangcun status        # 当前项目的同步状态与漂移
fangcun sync          # 按清单与锁物化
fangcun sync --frozen # CI 用：锁与清单不一致就失败
fangcun add <资产>     # 加入清单
fangcun update        # 检查并升级
fangcun why <资产>     # 解释它为何生效、来自哪一层
```

### MVP 明确不做

- 不管理会话状态类资产，例如记忆、任务进度文档。它们是「演化中的状态」而非「配置」，机制不同。
- 不做自建市场，不做账号体系，不做云同步。
- 不代理或拦截 Agent 运行，不做 MCP 网关。
- 不安装 CLI 依赖。只在后续版本做「依赖是否就绪」的检查。
- 不做 skill 质量评测。

## 6. 关键界面与体验流程

本节与高保真原型同步。原型共五张画板：设计系统「墨格」、项目页、体检报告、资产库、套装。线框图与原型里的数字、名称都是示意，不全是实测结果。

全局页（6.6）与活动页（6.7）还没有画板。这两节按「墨格」规范和已有画板的模式写成，示例数据与已有四张画板一致，待补进原型。补画板时，已有画板的侧栏也要在「活动」旁加上待处理数。

### 6.1 形态

- **主窗口**：自上而下是整窗工具栏，下面是侧栏、列表、检查器三栏。
- **菜单栏常驻图标**：显示漂移与可更新的角标，可快速跳到项目。角标数字与活动页的待处理数一致。
- **命令面板** `⌘K`：搜索资产、项目、动作。键盘优先。
- **命令行** `fangcun`：见上节。

**窗口骨架**，所有页面共用：

- **整窗工具栏**：高 40px，贯穿窗口顶部。从左到右依次是窗口按钮、后退与前进、侧栏开关。窗口控件只出现在这里，侧栏折叠与否都不影响左上角。
- **侧栏**：顶部是「方寸」标识，下面五个导航项：**项目**、**资产库**、**套装**、**全局**、**活动**。项目页下方列出已登记项目及其状态点。底部固定「重新体检」，下面一行小字「本地优先 · 零遥测」。侧栏可折叠为 56px 宽的图标栏，此时只保留导航图标。
- **列表与检查器**：选中列表中的一行，右侧检查器显示详情。检查器右上角有 × 关闭按钮，关闭后列表占满宽度；再点任意一行即重新打开。
- **分栏独立滚动**：窗口固定为一屏高，侧栏、列表、检查器各自滚动，滚动一栏时其他栏不动。窗口窄于 900px 时，各栏改为上下堆叠，整页滚动。

**检查器统一结构**：项目页、资产库、体检报告、全局、活动五处的详情面板用同一套结构，依次是类型小标签、名称、状态徽标、一句说明、字段表、若干分区、操作。分区标题统一用 11px 灰色小字，内容超出时出现细滚动条。

### 6.2 首次启动：体检报告

体检报告沿用主窗口骨架，主体是「发现列表 + 检查器」两栏，不另做弹窗。

```
● ● ●  ←  →  ▣
──────────────┬────────────────────────────────────────────────────────────
 方寸          │ 体检报告  ● 只读扫描完成，未改动任何文件     [稍后处理] [进入项目]
 项目       6  │ 处理进度 0 / 5   扫描了 7 个工具、61 个项目目录   重复副本 4
 资产库    38  │ ▭▭▭▭▭
 套装       3  ├───────────────────────────────────────┬────────────────────
 全局      31  │ 类别      发现                     状态   │ 体检发现             ×
 活动          │ ● 重复    project-harness 有 5 份…  待处理 │ project-harness 有 5 份副本
```

- 概要条与项目页的预算条同一样式。每处理一项发现，进度条点亮一段。
- 处理完的发现划线并标「已处理」，检查器显示「已处理 · 已留快照」和撤销，然后自动跳到下一条。
- 第一屏就给出价值，不要求先建库、先配置。

**页头**：项目名与路径、目标工具分段控件、漂移徽标、命令面板入口、「同步 · N」主按钮。切换目标工具后，列表只显示该工具实际加载的内容，例如 Codex 不读取 `CLAUDE.md`。

**预算条**：指令、Skill、MCP 三段，同一色相、三档明度，对照项目预算显示，始终标明「估算值」。

**生效上下文列表**：

- 按指令、Skills、MCP 分组。每行四列：名称与版本、层级刻度与作用层、状态、常驻估算。
- 最后一组是「其他加载项」，带「只看不管」标签，逐行列出插件、Hook、斜杠命令、子代理，列与上方资产对齐。这些行不可操作，不计入预算，未发现的类型用一行小字说明。

**检查器**：

1. 状态专属操作区，只在需要时出现：
   - 漂移：差异片段，回流、丢弃、分叉三选一，预览后应用。
   - 可更新：版本差异，脚本变更标红。
   - 全局税：在本项目停用，或改为套装。
   - 被覆盖：跳到覆盖它的项。
   - 来源未知：去资产库收编。
2. **为什么是这个状态**：用两句白话解释，下方附命令行的对应写法 `fangcun why <资产>`。
3. **在哪一层声明 · 谁覆盖谁**：全局、套装、项目、个人四行。生效的那层用绿底，被遮蔽的划线，停用的用橙色。
4. **上下文占用**：占本项目常驻的百分比，超过 30% 显示为橙色。
5. **写入了哪些文件**：实际物化的路径与软链指向，以及按键合并的配置项。
6. **最近活动**：这一项的时间线。

**清单页签**：顶部一句话说明清单的用途，下面三张文件卡可切换：

| 文件 | 角色 | 提交 |
|---|---|---|
| `fangcun.toml` | 项目清单 | 提交到 git |
| `fangcun.lock` | 版本锁，自动生成 | 提交 |
| `fangcun.local.toml` | 个人覆盖 | 不提交 |

默认是「结构化」视图，按区块用表格展示：项目设置，Skills（来源与版本策略，标注哪项来自套装），MCP 服务（启动命令与密钥位置），指令文件（正本与镜像）。可以切换到「源文件」视图，带行号，长行自动折行。界面上的改动会同步出现在两种视图里。

**历史页签**：快照列表，每条可「回滚到此」，当前磁盘状态有标记。

### 6.4 资产库

- **列表**：每行显示名称与来源、类型、使用中的项目数、状态。
- **筛选**：类型芯片（全部、Skill、MCP、指令）加一个「来源」下拉框，两者可以叠加。下拉框按本地开发、GitHub、npm、待收编分组，每项带资产数量；来源再多也只占一个控件。筛选结果为空时提供「清除筛选」。
- **详情**：与检查器同一结构。
  - 字段表：来源、正本、常驻、使用中、含脚本。含脚本时标红。
  - 版本：锁定中的版本用绿底标出。
  - 被哪些项目使用：每个项目的版本策略与物化方式。
  - 最近活动。
  - 来源未知的资产在底部提供「收编到资产库」。

### 6.5 套装

**套装**是一组常一起用的资产，起个名字给多个项目复用，例如「工程基线」「飞书办公」。它介于全局和项目之间：比装进全局更精准，不会给无关项目增加上下文负担；比逐个项目添加更省事。

- **左栏**：顶部是「新建套装」按钮，下面是「全部套装 · N」与套装列表。每个条目两行：名称与常驻估算、资产数与项目数。左栏可以折叠为首字方块组成的窄条，折叠后仍可切换和新建。
- **右侧详情**：
  - 清单写法 `bundles = ["<名称>"]`。
  - 包含的资产表：类型、版本策略、常驻。
  - 「哪些项目使用它」复选列表：勾选变化时标出「将加入」「将移除」，并给出常驻变化，确认后预览变更计划。

### 6.6 全局

**全局**是四层作用域的最上层，这里的每一项都会进入每个项目的上下文。这一页只回答一个问题：哪些东西值得让所有项目都付这笔常驻成本。

```
 全局基线  ~/.claude                 [Claude Code | Codex]  [⌘K]  [同步 · 0]
 全局常驻 6.9k / 项目预算 20k · 占 35% · 估算值    ■指令 0  ■Skill 6.9k  ■MCP 0
 ███████░░░░░░░░░░░░░
 [基线]  清单  历史
──────────────────────────────────────────────────────────────────┬──────────────────────────
 名称 · 版本                加载它的项目    状态            常驻  │ 已选 16 项               ×
 指令                                                             │ 常驻合计 6.4k · 占全局 93%
   没有全局指令文件                                               │ 瘦身预览
 Skills                                                           │  全局常驻   6.9k → 0.5k
 ☑ lark-* · 16 项 ▸         6 / 6           ● 全局税        6.4k  │  5 个项目   各减少 6.4k
 ☐ pr-review                6 / 6           ● 来源未知      0.3k  │  1 个项目   经套装继续加载
 ☐ frontend-design v1.1.0   4 / 6 · 2 覆盖  ● 可更新 ↑      0.2k  │ 哪些项目还需要它
   另有 13 项没有分发给 Claude Code ▸       ● 不一致              │  ☑ client-acme
 MCP                                                              │  ☐ evals_studio  将不再加载
   没有全局 MCP 服务                                              │  ☐ agent-lab     将不再加载 …
 其他加载项  [只看不管]                                           │ 怎么处理
   [插件] code-review-kit   6 / 6           含 2 个斜杠命令 0.3k  │  ◉ 转成套装「飞书办公」
   [插件] notify            6 / 6           含 1 个 Hook       —  │  ○ 降级到项目  ○ 从全局移除
                                                                  │ [还原]  [预览变更计划]
```

**页头**：标题「全局基线」、当前工具的全局目录、目标工具分段控件、命令面板入口、「同步 · N」主按钮。全局目录里的受管副本被改动时，页头出现与项目页相同的漂移徽标。

- 切换目标工具后，列表与概要条只算该工具实际加载的全局内容，页头的目录也跟着换，例如 Codex 下是 `~/.codex`。
- 侧栏「全局」旁的数字是全局目录里去重后的资产总数，示例中是 31。它可能大于当前工具下看到的行数。

**概要条**：与项目页的预算条同一样式，三段分别是指令、Skill、MCP。它对照默认项目预算给出占比，也就是一个项目什么都还没声明时已经用掉的份额。占比超过 30% 显示为橙色，始终标明「估算值」。

**页签**：基线、清单、历史，与项目页的三个页签一一对应。

**基线列表**：

- 按指令、Skills、MCP 分组，最后是带「只看不管」标签的「其他加载项」。空的分组保留标题，用一行小字说明，例如「没有全局指令文件」。
- 每行四列：名称与版本、加载它的项目、状态、常驻估算。项目页的第二列是层级刻度，这里所有行都在全局层，所以换成「加载它的项目」。
- 组内按常驻估算从高到低排列。全局的每一项对每个项目成本相同，所以这个顺序就是瘦身收益的顺序。
- 「加载它的项目」写成「6 / 6」。有项目覆盖或停用它时一并写明，例如「4 / 6 · 2 覆盖」。
- 来源相同的多个资产默认折叠成一行，例如「lark-* · 16 项」，可以展开。来源未知的资产不折叠。
- 全局目录里有、但没有分发给当前工具的资产，折成组尾的一行，例如「另有 13 项没有分发给 Claude Code」。展开后逐项列出。
- 行首有复选框，可以多选。

**状态**沿用「墨格」的六种状态语义，不新增颜色。每种状态在检查器里有对应的操作：

| 状态 | 颜色 | 含义 | 检查器里的操作 |
|---|---|---|---|
| 全局税 | 橙 | 常驻成本高，而多数项目近 30 天没有触发过它 | 转成套装，或降级到项目 |
| 已漂移 | 橙 | 全局目录里的受管副本被改动 | 看差异，回流、丢弃、分叉三选一 |
| 可更新 | 蓝 | 来源有新版本 | 看版本差异，审阅后加入同步计划 |
| 不一致 | 蓝 | 各工具分发不齐 | 补齐到所选工具，或标记为已知 |
| 来源未知 | 紫 | 不在资产库里，没有版本记录 | 去资产库收编 |
| 明文密钥 | 红 | 全局 MCP 配置里有明文凭据 | 移入钥匙串 |
| 已同步 | 绿 | 与全局锁一致 | 无 |

「全局税」的判定依据是本地会话记录里的触发情况。没有使用数据时不打这个标签，列表只按常驻成本排序。

**检查器 · 选中一项**：沿用统一结构。

- 字段表：位置、来源、版本、常驻、触发、含脚本。「触发」写近 30 天有几个项目用过它。含脚本时标红。
- 分区依次是：
  1. 状态专属操作区，只在需要时出现，内容见上表。
  2. **为什么是这个状态**：两句白话，下方附命令行的对应写法 `fangcun why <资产>`。
  3. **各工具的分发**：每个工具一行，写明已链接、实体副本或未分发。首批完整支持之外的工具标「只读」。
  4. **对各项目的影响**：每个项目一行，写明加载、被项目同名项覆盖、或已在该项目停用。点项目名跳到项目页并定位到这一项。
  5. **上下文占用**：占全局常驻的百分比，超过 30% 显示为橙色。
  6. **写入了哪些文件**。
  7. **最近活动**。
- 底部是「移出全局」入口，点开后与下面的瘦身面板相同，只是对象是这一项。

**检查器 · 选中多项**：选中两项以上时，检查器变成瘦身面板。

- 标题是「已选 N 项」，下面是常驻合计与它占全局的比例。
- **瘦身预览**：全局常驻的前后对比，以及有多少项目会减少多少。
- **哪些项目还需要它**：与套装页「哪些项目使用它」同一个复选列表。有使用数据时预先勾上近 30 天用过它的项目，否则都不勾。未勾选的项目标「将不再加载」。
- **怎么处理**：三选一的单选，控件与漂移的三选一相同。三个选项见下表。
- 底部是一句待确认的说明和两个按钮「还原」「预览变更计划」，与套装页相同。说明写清结果和数字，例如「将把 16 项移出全局，组成套装『飞书办公』，client-acme 继续加载。其余 5 个项目常驻各约 −6.4k（估算）」。

| 选项 | 结果 | 适合的情况 |
|---|---|---|
| 转成套装 | 资产移出全局清单，组成新套装或并入已有套装。勾选的项目在清单里引用这个套装 | 一组资产被几个项目共同需要 |
| 降级到项目 | 资产移出全局清单，逐项写进所勾选项目的清单 | 只有一两个项目需要 |
| 从全局移除 | 只移出全局清单。正本留在资产库，随时可以加回来 | 没有项目需要 |

- 变更计划按「全局」和每个受影响的项目分组。应用后只留一个快照，提示条带撤销，之后可以在活动页回滚。
- 转成套装后，新套装出现在套装页，可以在那里继续调整使用它的项目。

**同一件事的其他入口**：原型里已有三个按钮与瘦身有关，它们和全局页走的是同一套操作。

| 入口 | 按钮 | 做的事 |
|---|---|---|
| 体检报告的「全局税」发现 | 创建套装「飞书办公」 | 就地执行「转成套装」，默认勾选用过它的项目 |
| 项目页检查器 | 改为套装「飞书办公」 | 同上，从项目页发起 |
| 项目页检查器 | 在本项目停用 | 不动全局，只在这个项目的清单里写入停用。全局页「对各项目的影响」里，这个项目显示为「已停用」 |

**添加到全局**：用 `⌘K` 或列表顶部的「添加」。确认前显示成本，例如「加入后每个项目的常驻增加 0.4k」。全局层要尽量薄，所以这里特意多一步确认。

**清单页签**：全局层同样遵循「文件即真相」。版式与项目页的清单页签相同，上面是文件卡，下面是「结构化」与「源文件」两种视图。

| 文件 | 角色 | 标签 |
|---|---|---|
| `~/.fangcun/global.toml` | 全局清单 | 只在本机 |
| `~/.fangcun/global.lock` | 版本锁 | 自动生成 |

- 格式与项目清单相同。
- 全局清单不引用套装，也没有个人覆盖。套装的意义就是不进全局，而全局层本来就只属于你。
- 首次进入时由现状反推生成，来源未知的项原样列出并标「未收编」。
- 两个文件可以放进你的 dotfiles 仓库，换新电脑时一步还原。
- 其他命令行留下的全局锁文件不是方寸的清单。首次生成时读它作为来源线索。体检「脱节」发现里的「按目录重建锁」会把它重写成与目录一致，旧文件留有备份。

**历史页签**：与项目页相同，每行是快照编号、标题与时间，当前磁盘状态有标记，其余各行可以「回滚到此」。这里只列出涉及全局的快照。

**被其他工具改动**：别的命令行往全局目录装了新东西时，列表里出现一行「来源未知」，资产库的「待收编」分组和活动页的待处理里同时多一条。受管副本被改动时按漂移处理。

**空状态**：全局为空时只显示一句「全局基线是空的，每个项目只加载自己声明的内容」和「从资产库添加」入口。空的全局是目标，不当作问题提示。

**阶段**：列表、概要条、瘦身预览都不写文件，可以随 M0 提供。瘦身操作与清单编辑属于 M1。

### 6.7 活动

**活动**是所有项目与全局的统一记录，分两个页签：**待处理**收拢需要你决定的事，**时间线**记录已经发生的事。

第 5 节所说的「更新中心」就是待处理页签里的「可更新」类别，不再单独占一个导航项。原型里回流完成后的提示「它们会出现在更新中心」，指的也是这里。

活动相关的界面有三处，它们是同一份记录的不同切面：

| 位置 | 范围 | 用途 |
|---|---|---|
| 检查器的「最近活动」 | 单个资产 | 看这一项经历过什么 |
| 项目页与全局页的「历史」页签 | 单个项目或全局 | 在这个范围内回滚 |
| 活动页 | 所有项目、全局、资产库 | 处理待办、跨项目追溯与回滚、找回备份 |

**页头**：标题「活动」、命令面板入口、「同步 · N」主按钮。这里的 N 汇总所有范围里已加入计划的变更，变更计划按范围分组。

**入口与计数**：

- 侧栏「活动」旁显示待处理事项数，为零时不显示。其他导航项旁的灰色数字是存量。这个数字表示有事要处理，所以用橙色圆点加数字，与页头的漂移徽标同一样式。
- 菜单栏角标、项目页头的漂移徽标、侧栏项目名旁的状态点，与它是同一批事项的不同入口。在任何一处处理完，其他入口同时消失。
- 待处理不为空时默认打开「待处理」，否则打开「时间线」。

- 列表三列：类别、事项、范围，行样式与体检报告的发现列表相同。同一资产影响多个项目时合并成一行。
- 处理方式也与体检报告相同。处理完的事项划线并标「已处理」，检查器显示「已处理 · 已留快照」和撤销，然后自动跳到下一条。离开页面后，已处理的事项只留在时间线里。
- 待处理为空时显示一行「没有需要你决定的事」。

| 类别 | 颜色 | 何时出现 | 在检查器里怎么处理 |
|---|---|---|---|
| 漂移 | 橙 | 受管副本被修改 | 看差异，回流、丢弃、分叉三选一 |
| 可更新 | 蓝 | 来源有新版本。可能是上游的新提交，也可能是你在别的项目回流生成的 | 看版本差异，审阅后加入同步计划，或跳过此版本 |
| 待收编 | 紫 | 全局或项目目录里出现来源未知的新资产 | 收编到资产库，或标记为忽略 |
| 缺密钥 | 橙 | 清单引用的密钥不在本机钥匙串里 | 填入钥匙串 |
| 同步未完成 | 红 | 上一次同步中途失败 | 看失败的文件，重试或回滚 |

**可更新的细节**：

- 版本差异的写法与项目页检查器相同。脚本、hook、MCP 启动命令的变化标红，并写明「脚本变更」。
- 「受影响的项目」分两种情况：
  - 在项目清单里直接声明的，逐个列成复选项。跟随该来源的项目默认勾选。固定版本的项目默认不勾并标「固定」，勾上等于手动把它改到新版本。
  - 经套装引入的，写明套装名，不逐个勾选。升级作用于套装，使用该套装的项目一起变化。
- 按钮沿用项目页的「审阅后加入同步计划」。加入后显示「已加入同步计划」和「撤回」，应用仍由页头的「同步 · N」完成。
- 「跳过此版本」后这一条消失，来源再出新版本时重新出现。

**与体检报告的区别**：体检是对存量问题的一次性盘点，有自己的进度。待处理是日常持续出现的事项。体检里没处理的发现不会出现在这里。

**列表**：

- 按天分组，新的在上。每行四列：时间、事件、范围、发起方。
- 事件用「圆点加类别」开头，后面是一句话描述。留了快照的行带 ◆ 和快照编号。
- 范围是项目名、「全局」、「N 个项目」，或「全部」。
- 发起方有五种：界面、命令行、监听器、自动检查、自动。从终端或 CI 运行 `fangcun` 产生的事件同样记录在这里。
- 一次批量操作只占一行，可以展开看每个项目的明细。
- 体检里的处理动作也记在这里，按性质归类：收编归「收编」，转成套装与重建锁归「同步」，「标记为已知」归「系统」。

**筛选**：与资产库同一模式。类别芯片加一个「范围」下拉框，两者可以叠加。下拉框列出全局与每个已登记项目。「只看写入」隐藏所有观察类事件。筛选结果为空时提供「清除筛选」。

**事件的三种性质**：

| 性质 | 包含 | 能否回滚 |
|---|---|---|
| 写入 | 同步、收编、升级、回流、丢弃、分叉、回滚 | 能。每次写入留一个快照 |
| 观察 | 发现漂移、发现新版本、体检完成、适配器更新 | 不涉及。没有改动任何文件，行用灰色显示 |
| 密钥 | 存入、替换、删除钥匙串条目 | 不能。只记名称与位置，从不记录值 |

**快照编号**：全机统一递增。项目页与全局页的「历史」只列出涉及自己的快照，所以看到的编号可能不连续。跨项目的批量操作在每个相关项目的历史里是同一个编号。

**检查器**：沿用统一结构，类型小标签是「活动」。

- 状态徽标：已应用、已回滚、失败、仅观察。
- 字段表：时间、范围、发起方、快照编号。
- 分区依次是：
  1. **变更的文件**：这次实际执行的变更计划，写法与同步预览一致。
  2. **备份的内容**：这次变更覆盖或删除的原文件，例如被丢弃的漂移修改、收编前的原副本、重建前的旧锁。每份可以查看，也可以单独恢复。恢复同样先出变更计划。
  3. **涉及的资产**：点名称跳到资产库或项目页的对应项。
  4. **之后的变更**：同一范围内在它之后发生的写入。
  5. **相关事件**：例如「发现漂移」与随后的「回流」互相链接。
- 操作：写入类事件提供「回滚到这次变更之前」，是次要按钮。

**回滚规则**：

1. 回滚恢复的是快照。「回滚到这次变更之前」等于在「历史」页签里对上一个快照点「回滚到此」。
2. 回滚先出变更计划。计划里列出会一并撤销的后续变更，以及快照之后被外部改过、将被覆盖的文件。
3. 回滚本身是一条新的写入事件，也留快照。时间线只增不删，所以回滚也可以再回滚。完成后的提示条写明结果，例如「已回滚到快照 #125，磁盘状态逐字节一致」。
4. 跨项目的批量操作是一个快照。可以整体回滚，也可以只勾选其中几个项目。
5. 两样东西不随回滚恢复。钥匙串条目保持现状。收编进资产库的正本保留，它不占任何项目的上下文。
6. 提示条和检查器里的「撤销」是回滚的快捷入口，只对刚应用的那次变更有效。错过了就到时间线里回滚。

**留存**：

- 事件记录长期保留，只存在本机的 `~/.fangcun/` 里，可以导出为 JSON Lines。
- 快照和它的备份一起保留，默认 30 天，并且每个范围至少保留最近 20 个。这两个数是建议值，可在设置里调整。
- 快照也可以手动删除，「删除快照」是危险按钮。
- 快照过期或删除后事件仍然可查，回滚按钮置灰并说明原因。

**阶段**：M0 不写任何文件，时间线里只有观察类事件，待处理只展示不处理。处理动作与回滚随 M1 开放。

```

│  + .agents/skills/tdd            链接到 tdd@a1b2c3            │
│  + .claude/skills/tdd            相对链接到 .agents/skills/tdd │
│  ~ .mcp.json                     新增键 mcpServers.github      │

│                                                                │
│  不会触碰其他任何文件。                  [取消]   [应用 ⌘↩]    │
└───────────────────────────────────────────────────────────────┘
```

检查器里的停用、升级等操作先加入同步计划，由「同步 · N」统一预览和应用。应用后出现提示条，并生成一个快照。

变更涉及全局或跨越多个项目时，计划按范围分组，可以逐组取消。整批变更应用后只生成一个快照。

### 6.9 关键流程

1. **给项目加资产**：`⌘K` 搜索，回车加入，弹出变更计划，应用。全程不离开键盘。
2. **处理漂移**：点页头的漂移徽标，检查器定位到该资产，看差异，三选一。选「回流」时列出同样使用该资产的其他项目，逐个决定是否跟进。
3. **升级**：在检查器或活动页的「待处理」里看差异，脚本改动标红，加入同步计划后应用。不满意就在「历史」或「活动」里回滚。
4. **全局瘦身**：「全局」页按「给每个项目带来的常驻成本」排序。选中一批，在瘦身面板里勾选哪些项目还需要它，一步转成套装。之后可以在套装页继续调整。
5. **追溯与回滚**：发现 Agent 行为变了，打开活动页的「时间线」，按范围筛到这个项目，找到可疑的那次变更，看它改了哪些文件，回滚到它之前。

### 6.10 视觉与交互基调

视觉规范见设计系统「墨格」，要点如下。

- **原生 macOS 质感**：整窗工具栏、系统字体、深浅色成对定义并跟随系统。非 Mac 环境回落到 Inter 与 Noto Sans SC。
- **密而不乱**：
  - 正文 13px，行高 30px（紧凑）或 36px（标准）。
  - 间距以 4px 为单位递增。
  - 用灰阶层次和细分隔线分组，不堆卡片阴影。
- **一个强调色**：黛蓝（浅色模式 `#3552D4`，深色模式 `#7D93FF`），只用在可操作的元素和当前选中的状态上。
- **六种状态语义**：已同步、漂移、可更新、脚本变更、来源未知、被覆盖。状态一律用「圆点加短标签」表达，不只靠颜色。漂移用橙色，可更新用蓝色，避开红绿对立。
- **签名元素「层级刻度」**：四个 6px 小方格，依次对应全局、套装、项目、个人，实心格表示该项所在的层。标志取「方中之方」。
- **文件即真相**：路径、哈希、清单片段一律用等宽字体原样展示。
- **同一套交互模式**：
  - 落盘动作都是预览、确认、可撤销。
  - 面板都可以用 × 关闭。
  - 侧栏与列表都可以折叠。
  - 说明性文字能省则省，必要时折叠起来，不长期占用空间。
- **空状态即引导**：没有资产时直接展示体检入口，而不是空白表格。

## 7. 技术架构

### 7.1 选型建议

**Rust 内核 + Tauri 2 外壳 + React 界面。**

- 内核是独立的 Rust 库，桌面应用与命令行共用。这保证 CI 与界面的行为完全一致。
- Tauri 包体小，访问文件系统与钥匙串方便，将来上 Windows 与 Linux 不必重写界面。
- 备选是 SwiftUI 界面加 Rust 内核，Mac 质感最好，但跨平台时界面要重做。你明确提到未来全平台，所以不推荐。

### 7.2 模块

```
┌──────────────── 桌面应用 (Tauri + React) ────────────────┐
│   项目页 · 资产库 · 体检 · 更新中心 · 菜单栏 · ⌘K          │
└───────────────────────────┬──────────────────────────────┘
                            │              ┌── 命令行 fangcun
┌───────────────────────────▼──────────────▼───────────────┐
│                        内核 (Rust)                        │
│  扫描器 │ 资产库 │ 解析器 │ 物化器 │ 监听器 │ 估算器       │
│  ─────────────────────────────────────────────────────── │
│  适配器层：每个 Agent 工具一份声明式描述                    │
└──────────────────────────────────────────────────────────┘
        │                │                    │
   ~/.fangcun/      项目目录              macOS 钥匙串
   (正本与索引)   (清单、锁、物化产物)
```

- **扫描器**：遍历并归并，产出资产清点与体检发现。
- **资产库**：内容寻址存储，git 来源走本地裸仓库缓存，索引用 SQLite。
- **解析器**：合并四层作用域，解出确定结果，写锁。
- **物化器**：计划、应用、快照、回滚。记录所有权。共享的 JSON 与 TOML 按键合并。
- **监听器**：基于 FSEvents 监听已登记项目与全局目录，发现漂移。
- **估算器**：本地估算 token，明确标注为估算。

### 7.3 适配器是数据，不是代码

各工具的目录约定每月都在变，这是最大的工程风险。适配器因此设计为声明式描述，可独立于应用版本热更新。每份适配器声明：

- 各作用域下 skill、MCP、指令文件的读取位置
- 同名时的优先级规则
- MCP 配置的文件格式与字段映射
- 能力标记：是否跟随软链、是否支持项目级 MCP、是否支持按项目停用

工具不支持某项能力时，界面明确告知，不静默失败。每个适配器配一套回归样例，工具升级后自动验证。具体路径需在实现时对照各工具当期文档逐一核实，本文不写死。

### 7.4 清单示例

```toml
# fangcun.toml —— 提交到 git
[project]
targets = ["claude-code", "codex"]
mode    = "link"                 # link 或 vendor

bundles = ["工程基线"]

[skills]
tdd             = { source = "github:obra/superpowers", track = "main" }
skill-b         = { source = "github:acme/skills", pin = "v2.1.0" }
project-harness = { source = "local:luyao-skills", pin = "4d9b1eb" }

[mcp.github]
command = "npx"
args    = ["-y", "@modelcontextprotocol/server-github"]
env     = { GITHUB_TOKEN = "secret:github-token" }   # 值在钥匙串

[instructions]
canonical = "AGENTS.md"          # 正本
mirror    = ["CLAUDE.md"]        # 生成为对正本的引用
```

### 7.5 安全

- 锁里的内容哈希在每次同步时校验，来源被篡改会被拦下。
- 升级差异里，脚本、hook、MCP 启动命令的变化单独高亮。
- 写入范围限定在已登记项目与已知工具配置目录。每次写入前快照。
- 因为需要较宽的文件访问，不走 Mac App Store 沙盒。采用公证过的安装包与 Homebrew 分发。
- 默认零遥测。

| **M0** | 透视版，只读 | 扫描、体检报告、生效上下文视图。不写任何文件。零风险，先建立信任，也最快验证需求 |
| **M1** | MVP 闭环 | 收编、资产库、清单与锁、物化同步、漂移处理、更新回滚、基础密钥、简版套装、命令行。Claude Code 与 Codex |
| **V1.x** | 铺开 | 更多工具适配器。指令片段复用。斜杠命令、子代理、hook、插件纳入管理。CLI 依赖就绪检查。基于本地会话记录的使用洞察，提示从未触发的资产。提供方寸自己的 MCP 服务，让 Agent 能直接操作方寸 |
| **V2** | 团队 | 私有团队资产库、组织基线、准入白名单、更新审批、云端与 CI Agent 的引导脚本。Windows 与 Linux |
| **V3** | 质量 | Skill 效果对比试验。会话状态类资产的管理，例如记忆与进度 |

**衡量成功的四个指标**

- 首次价值时间：安装到看见体检报告的时长。
- 重复副本数：收编后应趋近于零。
- 来源已知率：有明确来源与版本的资产占比。
- 常驻上下文降幅：全局瘦身前后各项目的常驻估算值。

## 9. 风险与待你决策的问题

### 9.1 风险

| 风险 | 应对 |
|---|---|
| 工具频繁改目录与格式 | 适配器数据化、可热更新、带回归样例 |
| 厂商原生机制逐步覆盖需求 | 坚持跨工具中立与项目级闭环，原生机制能用就用，不重复造 |
| 赛道拥挤 | 用只读的 M0 快速验证「生效视图」是否真是差异点 |
| 写错用户配置造成损失 | 预览、快照、所有权记录、按键合并。M0 完全只读 |
| 软链在个别工具或 Windows 上不可靠 | 适配器能力标记，自动退回「复制加哈希跟踪」 |
| Token 估算不准 | 始终标注为估算，重在相对比较而非绝对数值 |

### 9.2 需要你拍板的六件事

我给出了推荐项。方案正文都按推荐项写成。

1. **技术栈**。推荐 Rust 内核加 Tauri 2。若你更看重极致的 Mac 原生质感且接受跨平台重做界面，可改 SwiftUI。
2. **首批工具**。推荐 Claude Code 与 Codex 完整支持，其余工具在 M0 只读扫描。你日常若主用 Windsurf 或 Trae，应调整顺序。
3. **默认物化方式**。推荐个人项目默认链接，检测到多人协作的仓库时建议入库，登记项目时询问一次。
4. **是否开源**。推荐内核与命令行开源。这个产品要写配置、碰密钥，开源是最便宜的信任来源，适配器也适合社区共建。团队功能留作商业化空间。
5. **清单格式**。推荐自有的 `fangcun.toml`，同时支持导入导出 `skills-lock.json`。不建议一开始就绑定某个现有格式，它们只覆盖 skill 一类。
6. **产品名**。「方寸」是我从目录名推断的，请确认。

### 9.3 建议的下一步

先做 M0。它只读、周期短、对你自己立刻有用，并且能用真实数据检验本方案最核心的假设：**「看见生效上下文」是否足以让人愿意把管理权交给一个新工具。**
