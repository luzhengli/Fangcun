# 方法层的摩擦

项目复盘时标了〔方法〕的摩擦抄到这里，写明来自哪个项目。至少两个项目都出现，才改方法。

- [ ] 2026-11-22 只有一个样本：判官分组、规则档位、度量口径都来自同一个项目，还没在别的形态（Web、命令行、库）上用过。
- [x] 2026-11-22 第一次盘点桌面应用项目的规则时，「从没被违反」把几条根本没人守的架构规则列成了删除候选：没人守时，没违反也许只是没被发现。〔方法〕→ 0.1.0 当场改：写了升档方案 `next` 的不算删除候选，rules.md 加一条提醒
- [x] 2026-11-22 Web 项目只读试跑：CLAUDE.md 软链到 AGENTS.md，常驻被算了两遍。〔方法〕→ 0.1.1 按真实路径去重
- [x] 2026-11-22 Web 项目把计划、日志、编排说明放在仓库根目录，探测只看 `docs/`，漏了。〔方法〕→ 0.1.1 根目录的 markdown 也算文档
- [x] 2026-11-22 两个项目都有「开工必读」：入口文件要求每次先读状态、计划、任务清单。只量入口文件会低估固定开销：Web 项目入口只有 46 行，加上开工必读是 17.5k 字符，是桌面项目的两倍。〔方法〕→ 0.1.1 配置加 `startup`，audit、metrics 按「自动加载 + 开工必读」算
- [x] 2026-11-22 在别的项目上试跑要先落 `.harness/config.json`，和「先只读看看」冲突。〔方法〕→ 0.1.1 全部命令加 `--config <文件>`
- [ ] 2026-11-22 Web 项目的待办是 `tasks.json`，audit 只会算 markdown 待办里已完成的占比。等第二个项目真用 JSON 待办时再定口径。〔方法〕
- [ ] 2026-11-22 Web 项目用「PLAN 只留一个 next_action + tasks.json」管状态，比 markdown 的「下一步」更好机读。status 还读不出 next_action，要不要支持，等那边落地时看。〔方法〕
