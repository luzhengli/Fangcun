# 上下文分层

长文档的代价不只是 token：常驻规则越多，每条被遵守的概率越低；结果太多会被截断、漏看；同一件事写几处，改一处漏一处；每轮收工都要维护。

按「谁、什么时候读」分层，而不是按主题：

| 层 | 放什么 | 怎么控制 |
| --- | --- | --- |
| 常驻 | 项目是什么、去哪读什么、几条最硬的规则、谁说了算、交流语言 | `budgets.entryLines`，默认 120 行。超了就把只在特定场合用的流程挪成 skill |
| 触发 | 只在做某件事时用的整套步骤：同步设计稿、发布、复盘、照设计稿实现一页 | 一件事一个 skill，或者本 skill 的一个 reference |
| 查询 | 规格、决定、架构 | 长不要紧，要好检索：章节索引、编号、`harness find` |
| 生成 | 分支、PR、计数、哪些东西落后了 | 由 `harness status` 和项目自己的脚本算，**不手写**。手写的副本迟早过期 |
| 归档 | 已完成的待办、旧日志 | 按里程碑挪到 `archive/`，查询脚本仍然覆盖 |

## 几条做法

- **状态文件只留判断。** 下一步做什么、为什么卡住、接手要注意什么。事实交给脚本。
- **工作日志能被 git 和 PR 代替时就不写。** PR 描述写清楚做了什么、没做什么；没有 PR 的讨论，结论进决定文件。
- **一件事只写一处。** 常驻文件里放指针，不放副本。
- **规则升到机器档以后，从常驻文件里删掉原文**（见 `rules.md`）。
- **`harness audit` 报出的「最长的几节」**，就是常驻文件最该挪走的候选。
