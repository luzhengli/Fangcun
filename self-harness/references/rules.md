# 规则阶梯

同一条要求，可以落在不同的强度上。档位越低越可靠，越不占 Agent 的注意力。

| 档 | 名字 | 含义 | 常见做法 |
| --- | --- | --- | --- |
| 1 | 写不出来 | 违反了跑不起来 | 类型、模块可见性、权限 deny、把参数写死的包装脚本 |
| 2 | 做错就拦 | 提交、CI 时报错 | lint、测试、PreToolUse 一类的拦截 hook |
| 3 | 适时提醒 | 在该看的时候冒出来 | 状态脚本、收工 hook、CI 警告 |
| 4 | 按需加载 | 做某件事时才读到 | skill |
| 5 | 常驻规则 | 每次会话都装进上下文 | AGENTS.md / CLAUDE.md |
| 6 | 查询文档 | 想起来才去查 | `docs/` |

## 升档、删除的判据

- **违反过一次就是证据**，至少升一档。证据来自摩擦记录、被推翻的决定、返工。
- **值不值得升**：违反的代价 × 频率，对比机械化的成本。频率低、代价小的，第 3 档提醒就够了。
- **删除**：停在第 5、6 档、从没被违反、也没起过作用的，删掉或降到第 6 档。确实要留的，在 `keep` 里写理由。
- **小心「从没被违反」**：没人守的规则，没被违反可能只是没被发现。这类规则先写一个便宜的检查（`next`），跑一次看看再决定删不删。
- **升到第 1、2 档以后，从常驻文件里删掉原文**，只在查询文档里留一句「由 X 守着」。机器守住的规则不必再让 Agent 记着。这是给常驻文件瘦身的主要办法。

## 记录格式

`.harness/rules.json`：

```json
{ "rules": [
  { "id": "R-01", "text": "颜色只用设计 token，组件里不写色值",
    "source": "docs/ARCHITECTURE.md#不能破的规则", "level": 5,
    "guard": "token 取值有测试；组件里写色值没人守",
    "violations": [ { "date": "2026-11-21", "ref": "摩擦：…" } ],
    "next": "lint：组件文件里出现 #rrggbb 就报错" }
] }
```

- `level` 写**现在最强的那道守卫**的档位，不是规则写在哪。
- `guard` 写具体是什么在守。
- `violations` 每次违反加一条，带日期和出处。
- `next` 写升到哪一档、怎么做。

`harness audit` 会列出升档候选（第 4 档及以上、被违反过）和删除候选。

## 常见的升档做法

- 固定参数的命令（模型、沙箱、标准输入）→ 包装脚本（第 1 档）。
- 「先读两遍再发布」这类步骤 → 包装脚本，或者一个只讲这件事的 skill（第 4 档），或者拦截 hook 查会话记录（第 2 档）。
- 「收工要更新状态」→ 收工 hook：改了代码没改状态文件时提醒（第 3 档）。
- 「某目录不许出现某些词」→ `config.json` 的 `boundaries`，`harness check` 进 lint（第 2 档）。
