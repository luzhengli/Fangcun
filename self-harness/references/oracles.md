# 判官清单

判官是对一个质量维度给出「过 / 不过」的东西。Agent 能在哪里放手，取决于那里有没有可信的判官。

## 衡量一个判官

- **谁下结论**：四档。`机判`：机器给过或不过。`机证`：机器取证据，Agent 或人看了再下结论（截图对比、差异占比）。`人判`：只能人看。`无`：没人守。
- **可不可信**：误报多的判官比没有更糟，大家会学会无视它。偶发失败的测试、噪声大的像素差，都要单独记一笔。
- **多早发现**：写代码时 < 提交时 < CI < 合并后 < 真机或用户。越晚越贵。

## 怎么列

按五组过一遍，每组想「这个项目里，什么算做坏了」：

| 组 | 问的是 | 常见判官 |
| --- | --- | --- |
| 正确性 | 做得对不对 | 单元、集成测试；和外部工具的对照 |
| 守规矩 | 有没有破项目的硬规则 | lint、类型、可见性、架构测试、grep 级检查 |
| 符合意图 | 做的是不是人要的 | 规格可追溯、截图对比、「定没定过」查询、人的基线 |
| 体验 | 好不好用 | 真机、无障碍、性能预算、人 |
| 流程 | 交接和文档有没有跟上 | 状态脚本、hook、CI |

写进 `.harness/oracles.json`：

```json
{ "oracles": [
  { "group": "正确性", "dimension": "核心逻辑", "oracle": "单元测试", "grade": "机判",
    "when": "提交前、CI", "trust": "并发相关偶发失败", "next": "并发测试循环跑 20 次" }
] }
```

`grade` 只能是 `机判`、`机证`、`人判`、`无`。`next` 写补缺口的下一步，没有就不写。

## 怎么用这份清单

- **看缺口落在哪组。** 返工最贵的地方，通常是判官最少的那组，常常是「符合意图」。往判官已经很密的组里加测试，收益小。
- **人判一次，机器守以后。** 人验收过的截图存成基线，人拍板的决定能写成测试或 lint 的就写。人的判断只用一次就丢掉，是最大的浪费。
- **意图层做不到全自动，就做到可追溯。** 给规格里的要求编号，测试和截图场景标上自己守哪一条，就能列出「没有任何判官的要求」。
- **不可信的判官先修。** 修好之前，在 `trust` 里写明，别让 Agent 把它的通过当成证据。
