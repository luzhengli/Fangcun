# 复盘与进化

harness 按「摩擦 → 归类 → 升档 → 记录」迭代。skill 自己也一样。

## 记摩擦

流程上的卡点（等人传话、重复劳动、返工、缺工具、规则互相打架），当场记一条，放在 `config.friction` 指的文件和标题下：

```
- [ ] 2026-01-31 现象：谁卡住了，耽误了什么。〔方法〕
```

- 日期打头，度量要用。
- 结尾标 `〔方法〕` 的，是这个 skill 的方法、脚本、口径的问题；不标的是项目自己的问题。

## 什么时候复盘

摩擦攒到阈值（`config.friction.threshold`，默认 5），一个里程碑结束，或者人说「复盘」。

## 怎么复盘

1. `harness metrics --record`，留一个复盘前的快照。
2. 把没勾的摩擦归类，每类出一个改进项，写进项目的待办。
3. 每个改进项先问能不能升档（`rules.md`）：写成脚本、lint、hook，比写成文字强。只能写文字的，写进触发层（skill），别写进常驻文件。
4. 能做的当场做。做完勾掉对应的摩擦，注明改进项编号。
5. 涉及的规则在 `.harness/rules.json` 里补违反记录、改档位；涉及的判官改 `oracles.json`。
6. 再跑 `harness audit`，确认没有新的超预算。

## 看什么

一轮里人要介入几次、介入是拍板还是纠错；交接等了多久；同一件事返工几轮。

## skill 自己的进化

- 标了 `〔方法〕` 的摩擦，复盘时抄一份到 skill 的 `FRICTION.md`，写明来自哪个项目。
- 只在一个项目出现过的做法不进 skill；至少两个项目都用得上，才改 SKILL.md、references 或脚本。
- 每次改动在 `CHANGELOG.md` 记版本、改了什么、证据。
- 项目里对 skill 的本地修改算漂移：好的回流到 skill，不好的丢弃，只对本项目成立的分叉到项目自己的文档或脚本里。
