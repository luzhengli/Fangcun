# 度量

只回答一个问题：harness 有没有让 Agent 在质量不降的前提下更自主。人的成本、质量、harness 自身的成本，三样一起看，缺一样都会被误导。

`harness metrics` 现在能算的：

| 指标 | 量什么 | 怎么算 | 局限 |
| --- | --- | --- | --- |
| 改文档的行数占比 | harness 的维护成本 | git 近 N 天的改动行，路径属于 `config.docs` 的算文档 | 设计期文档本来就多，看趋势 |
| revert 次数 | 返工 | 提交标题以 revert 开头 | 很多返工不走 revert |
| 每周摩擦条数 | 流程顺不顺 | 摩擦记录里带日期的条目 | 取决于有没有人记 |
| 常驻字符数 | 每次会话的固定开销 | `config.entry` 文件的字符数 | 不含平台自己加载的记忆 |
| Agent 定 / 被推翻 | Agent 理解意图准不准 | 决定、待办文件里按 `decisionsMetric` 的两个模式数行 | 关键词粗估。收工时在被推翻的条目后补「推翻」，口径才稳 |
| 规则按档、判官按档 | 机械化的程度 | `.harness/` 两份清单 | 清单要跟着复盘更新 |

还没自动化、值得手记的：

- **人每批介入几次、为什么**：拍板、验收算正常成本；传话、纠错算 harness 的缺口。收工时在状态文件或 PR 里记一句。
- **合并后才发现的问题**：在待办里给这类条目加一个固定标记（例如「合并后发现」），以后脚本就能数。

## 约束

- **只看趋势，不设目标。** 设了目标，Agent 会去凑数字。
- **样本小，别过度解读。** 一个月几十个提交，变化一两个百分点不说明什么。
- **`--record` 在复盘前后各记一次**，看复盘有没有用。
